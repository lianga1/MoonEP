八卡训练通信估算：模型与边界
更新日期：2026-11-05

1. 这份估算回答什么

保留 router dump 的八个来源 rank、八个执行 rank，不把它折叠成两卡。两张
H200 只用于测量单个通信操作的有效带宽和原八卡尺寸下的 kernel 时间。八卡
结果是基于流量矩阵的估算，不是八张物理 GPU 的端到端训练实测。

原 trace 每层形状为 [8,16768,8]：N=134144 个 token，每个 token 选择 K=8
个专家，E=352；原始专家 home[e]=e//44。来源是原始 token 所在卡。执行位置
由各算法的 owner 计划确定。当前八层对照是 native_rt0、native_rt2，以及
sample256_g2_bundle（d=256、每类两组、L=4）。rt0 仍会为负载均衡复制专家；
rt2 的 2 是每卡先尝试保留的流行专家数，不表示总副本最多两个。

输入证据是 outputs/eight_rank_estimate/traffic.json。每种方案独立检查原任务
恰好执行一次、专家任务守恒、计算对负载均衡、专家驻留合法和每卡附加槽 B=8。
两卡校准原始文件的失败轮次必须保留；只从 status=complete 且正确性通过的
case 计算有效带宽。由每个 sample 的两 rank 较慢值先取 max，再取中位数。

2. 哪些数据真正过链路

每层定义 D[s,d]：原在来源卡 s 的 token 中，至少有一个计算对被分给卡 d 的
token 数；s=d 置零。同一 token 的三个专家都在 d，只传一份 hidden，不能按
三个计算对重复收取 hidden 字节。Q[s,d] 则是计算对数；路由权重等每专家标量
可能按 Q 传输，不与 hidden 一起去重。当前主解析式只计 hidden、专家参数和
参数梯度，不计路由标量、协议头、对齐填充。真实校准计时会包含实际 kernel
的相关标量和同步开销，所以估算不是精确的链路字节计数。

H 是 hidden 向量长度，b_x 是一个元素的字节数。一次前向与反向有四个 hidden
传输阶段，矩阵的行始终是数据发送者、列始终是数据接收者：

  前向 dispatch： A_x  = H*b_x *D
  前向 combine：  A_y  = H*b_y *transpose(D)
  反向 dispatch： A_dy = H*b_dy*D
  反向 combine：  A_dx = H*b_dx*transpose(D)

反向须使用前向保存的同一计划和去重映射。这里假设四种 hidden 均为 BF16，
所以训练 token 总字节 = 4*H*2*sum(D)。实际训练若用 FP32 激活梯度，应改
b_dy/b_dx；不能因为专家参数梯度是 FP32，就把 hidden 梯度也自动当成 FP32。
前向/反向 GEMM、真正的反向数学、optimizer、保存激活、重算、DP/TP 同步均不
在本估算中。不能将通信回放称为完整训练。

定义 C[h,d]：原专家在 home 卡 h，需要复制到卡 d 的附加槽个数。一个专家复制
到三张卡就是三份。当前 MoonEP 会拷贝每个非负 experts_to_copy 条目，没有
自动的专家 ID/权重版本缓存跳过。模型按实际需刷新的槽计数，不按去重专家数。
本地原有的 44 个专家不收费。home 到 replica 的 BF16 权重和 replica 回 home
的 FP32 梯度矩阵为：

  P = 3*H*I                         （三块 dense 权重；没有 bias）
  W = 2*P*C
  G = 4*P*transpose(C)

I 是专家中间维度；假设 H=7168、I=2048，则 P=44,040,192，权重每份 84 MiB，
FP32 梯度每份 168 MiB。参数梯度返回虽然由 home 发起远端读取，数据方向仍是
replica -> home。各算法都计自己的 W/G；比较时再相减，不能把原生副本费用设零。

已独立校验八层计数：rt0/rt2/优化分别是 71/203/507 个需要复制的专家槽。每层
只刷新一次权重时，优化比 rt0 多 436 份，额外权重 35.765625 GiB、梯度
71.53125 GiB；四次 token 通信合计
节省 67.424774169921875 GiB。因此 M=1 的总 payload 字节反而增加
39.872100830078125 GiB。字节不是时间；还需看最忙端点和各类实测带宽。

3. 从矩阵到时间：不能拿总字节除以一个链路带宽，也不能机械除八

对任一操作的字节矩阵 V，先算每卡：
  TX_i = sum_j V[i,j]                 这张卡发送的总字节
  RX_i = sum_j V[j,i]                 这张卡接收的总字节
  endpoint_bytes(V) = max(max_i TX_i, max_i RX_i)

当前基础模型使用单向有效带宽 B（decimal GB/s）：
  T_ms(V) = endpoint_bytes(V)/(B*10^6)

这是同一台无阻塞 NVSwitch 服务器、八卡同时收发、每卡端点能力相同的简化模型。
它不假设任意两卡能同时各自占满整卡所有链路。若知道更多拓扑限制，应取下列
限制的最大值，而不是把这些互相重叠的限制相加：
  max_i TX_i/Btx_i；max_i RX_i/Brx_i；
  max_i (TX_i+RX_i)/Bduplex_i（仅当有共享双向总预算时）；
  max_ij V[i,j]/Bpair_ij；sum_ij V[i,j]/Bfabric（仅当已知交换机总预算时）。
后两项的容量未知，不伪造具体数值。RDMA、跨节点、CPU 互连和交换机超卖均不
在默认单机假设内。

反例：总共 560 MiB，若八卡每对各发 10 MiB，每卡最多发/收 70 MiB；若一张卡
向其余七卡各发 80 MiB，最忙卡发 560 MiB。同样总字节，端点瓶颈差八倍。
实际 L0，rt0 与 rt2 的总远端 token 是 621511 与 611019，下降 1.688%；但最忙
发送/接收端点仅从 78588 降到 78340，约降 0.316%。权重最忙端点却从 4 份变
7 份。这正是不能只用总 token 降幅推断时间降幅的原因。

逐层必须先算 T，再把八层相加：sum_l T(V_l)。不能先把矩阵加在一起再取 max，
因为每层最忙的卡可以不同。当前也不允许跨层通信互相隐藏。

4. 两卡带宽到底是什么

主校准选择 dispatch_S65536、combine_S65536、weight_8_8、gradient_8_8。
每个 sample 先取两 rank 较慢 CUDA 时间；带宽分子是所有端点中最大的单向
发送或接收 payload，分母是该时间。对称双向各 P 字节时，分子仍为 P，不能
把 2P/t 的双向聚合带宽拿来除单向矩阵。非对称情况同时保留两方向 payload。
Hopper 标称每 GPU 900 GB/s 是双向总量，不能当单向 900；本模型采用实测值，
不靠厂商理论数替换校准。

S16768、小副本数、单向 0_1、非对称 1_8/8_1 的 case 作为规模/方向敏感性
范围保留。dispatch 使用已有 dedup map，构建该表的成本不在该校准中。combine
有效带宽包含其局部归并等实际执行成本。不可再把同一 HBM 开销额外加一遍。
这些是特定操作的有效吞吐，不是纯物理链路速率。八 rank 的元数据、同步、七个
peer 并发、GPU 资源争抢和多副本归并都未在两卡校准中测到。

另一个重要差别：S65536 校准每个 token 是 4 个本地任务加 4 个远端任务，远端
只有一个目的地；原八卡每来源只有 16768 个 token，但一份 token 常发往多个
目的地，每个目的地承担的任务较少。同为 K=8 不代表本地 HBM 和传输操作的
比例相同。有效带宽可能向两个方向偏移，不能把默认估算的负收益当成物理上
不可能优化的证明。脚本另外给出 token 带宽独立变为 200/300/450 GB/s、专家
权重和梯度维持校准值的情景，并计算 token/专家相对速率改变时的回本阈值。

特别地，gradient_8_8 的每个 home 专家只有对端一个副本；八卡可能把同一专家
复制到多卡，当前 native reducer 按槽循环累加，八路有效梯度吞吐可能更低。
因此 f_gradient 必须能独立设置，不能认为所有类型都有相同缩放。

基础输出给出效率 1.0、0.75、0.5 三档：B_type,8 = B_type,2*f_type。
这些是假设的敏感性，不是置信区间。支持 token、weight、gradient 各自的效率
因子；同一档中基线和优化必须使用同一组因子，避免给优化单方面更好的带宽。
两卡波动区间也不代表八卡模型误差的统计置信区间。固定启动和 barrier 可能
造成非线性；用大包有效带宽线性推算是近似，不保证小流量精度。

5. 权重预取最多能遮住多少时间

专家方案就绪时刻 tE，token 方案就绪 tT；余下 planner 时间 Ptail=tT-tE。
独立权重时间 TW，dispatch 时间 TD。假设二者完全无资源冲突，从 tE 算起，
两者都完成的理想时刻为 max(TW, Ptail+TD)。可隐藏权重上限是
min(TW,Ptail+TD)，可见权重尾部为 max(0,TW-Ptail-TD)。这是上界：真实二者
共享发送/接收端点、HBM 和 SM，时间可以比串行更差，既有两卡证据已出现争抢。

本估算给两种清晰界限：
  全额串行： F*Tweight + 2*Tdispatch + 2*Tcombine + Tgradient
  理想权重全隐藏： 2*Tdispatch + 2*Tcombine + Tgradient
F 是每层一次前向加反向期间刷新专家权重的次数。默认 F=1 假定副本从前向一直
保留到反向，或只执行单层前向加反向；不能据此声称多层共享槽训练实际只传一次。
后一种只是最乐观下界，不是已实现效果；同时给基线和优化隐藏其所有权重。
梯度仍然全计，不未经验证就拿它与未知 GEMM/optimizer 互相隐藏。若做更细
资源模型，可把共享链路工作量 W+A 放到同一容量约束里，并考虑释放时刻；
不能仅凭两个 CUDA stream 的时间区间重叠就认为实际带宽时间已被隐藏。

共享端点服务近似对每个权重刷新窗口计算
max_i(W_TX_i/Bw + D_TX_i/Bd, W_RX_i/Bw + D_RX_i/Bd)，再加其余阶段。
F=1 时只尝试在前向 dispatch 窗口重叠；F=2 时一次配前向 dispatch、另一次
配反向 dispatch。不可把反向前才能进行的第二次刷新都放进前向窗口。这个近似
使用包含 SM/HBM 工作的有效带宽，不是严格的物理网络下界，也未获得真实重叠
测量的保证。

6. M 个微批的边界

M=1 是本轮主结果：一次 optimizer 更新含一次前向和一次反向、一次 FP32 副本
梯度返回。默认每层一次权重刷新具有上述保留前提。通常多层先执行 F0...F7、
再执行 B7...B0；共享槽被后续层覆盖后，求 dX 等反向计算仍需要专家权重，因此
可能在反向前再预取一次。最后一个前向层的副本也可能尚在槽中，不能简单声称
真实八层一定正好刷新 16 次。已有单层训练通信回放没有验证这个多层生命周期。

脚本支持 --weight-refreshes-per-layer=1 或 2，并总是保留两种敏感性情景。
F=2 表示每层一律刷新两次，作为明确的估算假设；梯度仍一次，token 仍四次。
相对 rt0 的额外权重变成 71.53125 GiB，额外 FP32 梯度仍为 71.53125 GiB，
总 payload 净增加 75.637725830078125 GiB。它不是对实际调度调用次数的断言。

固定映射、固定权重版本、所有相关副本和梯度
缓冲一直保留时，理想 M>1 为 W + sum_m 四次 token + G。若只能重放同一 trace，
只能称为“同流量重复 M 次”的情景，不能声称下一微批路由真的相同。

仅“映射不变”不够：当前 MoonEP extra slots 是跨层共享池，下一层可覆盖上一
层权重。默认执行不会自动获得 W 每 update 一次。必须额外持久化每层副本、
改变调度或明确检查 layer/expert/slot/version 后跳过预取；累积梯度也必须有
独立且存活的缓冲。如果映射变了，要先把被覆盖副本的累积梯度归回 home，再
安装新权重，按安装和 flush 事件收费。重算与流水线会改变实际调用次数。
因此多微批回本结果只给适用条件下的解析值，不标为硬件实测。
F=2 敏感性中的微批回本仍额外假定这两次刷新可在整个更新内摊销，不能由共享
池实现自动得到；每个微批重复刷新的真实调度需要逐调用计算。

7. planner 和“正收益”的判定

本次已新增八 rank GPU 组件，其是否通过以及时间以正式 kernel 结果为准；
完整八 rank 分布式 planner 仍未测。旧 H100 交换报告把 support 预先固定；
R2 residency kernel 硬编码两 rank，不能借它代表八 rank。
本模型先把额外 planner 设为 0，输出每层及八层总允许增量：
  允许额外 planner 毫秒 = 基线通信估计 - 优化通信估计。
该值为负时，即使 planner 免费，当前假设下通信本身也亏损。为正只说明存在
预算，不代表完整 planner 已经满足。比较 native_rt0、native_rt2 各自独立。

若后续测原八 rank 分片 kernel，使用原每来源 S=16768、R=8 索引与统计表。
在两张 GPU 上串行跑八份逻辑 shard，不能直接把累计时间除四或除八当八卡时间；
可报告每 shard 测量并用 max 作理想并行分量，原八卡 collective 另外估计。
带宽、流量模型、kernel 实测和完整训练端到端必须始终分栏。估算正值不能作为
本实验默认采用优化的依据，最终需要真正八卡训练路径的正确性、显存和端到端
验证。JSON 的 default_enable_optimized=false 表示本实验没有完成此验证，
不表示存在或修改了生产开关。
