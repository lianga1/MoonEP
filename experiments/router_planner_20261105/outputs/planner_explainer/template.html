01 / 先把两件事分开

抽 256 个 token，不是只优化 256 个 token。这 256 个用于观察“哪些专家一起复制可能有用”。复制位置选好后，仍检查这一层的全部 134,144 个 token，做四轮交换。

先有一个能运行的起点原生 MoonEP 把每张卡的计算对数量均衡。我们保留它要求的专家副本。
再挑额外专家位置查看全部或抽样 token，寻找有希望的双向交换，为缺失专家预留复制槽。
最后真正改任务分配在固定专家位置下，全量检查可交换任务；数量相等、专家可执行，才提交交换。

这里的“planner”是生成执行计划的程序。文档主要分析我们在原生 MoonEP 之后添加的交换方法。原生包本身没有这套 256 样本候选选择。

“没有采样”有两种含义：①不挑新副本，沿用现有副本直接交换；②用全部 token 挑副本，再交换。前者省掉选副本，后者保留完整搜索。它们不能用同一个复杂度概括。

02 / 名词都对应一件具体的事

词语这里的意思
GPU / CPU / kernelGPU 是并行计算芯片；CPU 是运行控制与本地仿真程序的通用处理器；kernel 是在 GPU 上执行的一段并行程序。
router / tracerouter 是决定每个 token 选择哪些专家的模块；trace（这里也叫 router dump）是把这些选择保存下来的记录。
rt0 / rt2原生热门专家保留数量分别设为 0 / 2。rt2 每卡主动挑两个非本地热门专家，均衡还可能引入其他副本；并不代表总副本数等于 2。
贪心 / 候选候选是尚未采用的可选方案；贪心是每次选择眼前评分最高的方案、更新状态再选，不保证整个问题的最优解。
token模型当前处理的一行数据；不一定等于一个汉字。trace 中保留的是这一行选中了哪些专家。
expert / 专家一个执行计算的子网络。要在某张 GPU 上执行它，那里必须有其参数。
rank参与协作的进程编号；本实验一个进程对应一张 GPU，编号 0～7。
top-k，K每个 token 选中的专家数量。这份数据 K=8；不是在选择 8 张卡。
计算对一次“某 token 由某 expert 处理”的任务。一个 token 有 8 个这样的任务。
home / 原属卡专家原本所在的 GPU。当前回放假设专家编号除以 44 取整得到原属卡。
owner / 当前执行卡某个计算对现在安排在哪张卡上执行；可以不同于 token 来源卡和专家原属卡。
驻留 / support一张卡允许执行哪些专家的清单。选中驻留表示计划准备参数，并不表示仿真真的复制了权重。
副本预算 B每卡除原属专家之外，最多再放多少个不同专家。本实验 B=8，必需副本也算在内。
组 / bundle同一个 token、同一个当前执行卡上的若干专家任务。后文区分完整组与交换时选出的部分组。
桶 / bucket按相同条件归类的一份提议名单，好比按方向和件数分开的等待队列。
采样种子伪随机数生成器的起始设置。输入顺序、软件版本和种子相同，可以重现同一批样本。
收益 gain少发了几份远端 token 数据。一次单向提议的收益通常是 0 或 1；不等于少算了任务。
其余实现词语：前缀、直方图、位图、掩码、哈希、元数据

直方图就是分类计数表。前缀是“到当前位置为止”的累计数量，用于给任务分配不重叠的编号。位图用每个二进制位表示某个条件是否成立；掩码是用于标记哪些位置有效或选中的标记表。哈希是将一组内容映射到简短编号的办法，可能出现不同内容得到同一编号，所以不能只凭编号认定组完全相同。元数据是专家编号、目的卡和数量等描述信息，不是 token 主体或专家权重。

gate 权重是专家输出合并时的加权系数；padding 是为满足对齐而补出的占位数据；梯度是训练中用于更新参数的信息；吞吐是单位时间完成的任务量。置信区间表示统计估计的不确定范围，这里的三个种子结果没有构成正式置信区间。μs 是微秒，ms 是毫秒。

通信的计数单位是“一个 token 发给一张远端卡一次”。一个 token 有三个专家都在同一张远端卡，只需计一份主体数据。实际字节数还取决于数据宽度、精度、权重和元数据，不能把这个计数直接叫作总通信字节。

03 / 动画：为什么要成组、为什么要双向

教学例子：u、v 都来自卡 C。只画 5 个计算对，其他本地任务省略。u 的 e1、e2 在 A，e3 在 B；v 的 f1、f2 在 B。最初 A 有 2 个任务，B 有 3 个。

远端 token 份数3
A 的任务数2 → 2
B 的任务数3 → 3

u 的完整组 {e1,e2} 从 A 去 B 后，u 不再需要访问 A，且原本就访问 B，因此节省 1 份。v 的 {f1,f2} 从 B 去 A，只是更换一个远端目的地，收益为 0。两者各交换两个任务，合计节省 1 份，两卡负载保持不变。

若只移动 u 的 e1，u 仍需访问 A 计算 e2，通信没减少。若只移动 v 的 f1 到 A，v 还要访问 B，反而多一个目的地。这说明为什么有些机会必须整组移动；并不意味着所有输入都需要整组才能获益。

全量交换如何避免相互打架？

  1. 每轮根据当前分配重新评估每个 token，最多选一个移动提议。目标卡必须已拥有涉及的专家。
  2. 将提议按“起点、终点、任务数量、收益”分类。收益为负的提议不进入普通交换。
  3. 在相反方向、相同任务数量之间匹配，优先选收益为 1 的提议。普通模式不提交双方收益都为 0 的交换。
  4. 同一轮每个 token 最多出现一次，所以提交时不需要解决两个提议同时改同一个 token 的冲突。下一轮再重新评估。

例如 A→B 有 3 个“移动 2 个任务、收益 1”的提议，B→A 有 2 个“移动 2 个任务、收益 0”的提议，就能匹配 2 对。双方各移动 4 个任务，节省 2 份 token 数据；第三个正向提议等待以后机会。

这叫“按桶匹配”：只需统计各名单有多少人，计算准入数量，再按名单内序号选中前若干个。没有逐一比较所有 token 对。没有反向伙伴时，即使单向移动有收益，也不能在本轮采用。

04 / 抽样究竟从哪里抽？

输入是一层的 [8, 16768, 8] 专家编号数组：8 张来源卡，每卡 16,768 行，每行 8 个专家。先把前两维展开成 134,144 行，再从这些完整的 token 行里均匀、不放回地抽 256 行。每个 token 被抽到的概率相同，同一轮不会抽中同一行两次。

rng = np.random.default_rng(seed)
chosen = np.sort(rng.choice(134144, 256, replace=False))
# chosen 是 token 的全局行号；每行带走全部 8 个专家及当前执行卡
source_rank = global_row // 16768
local_token_row = global_row % 16768

排序只让样本按原始行号处理，不是挑前 256 行。不是抽 256 个专家，也不是抽 256 个计算对；不是每卡抽 256 行，也不保证每卡恰好抽 32 行。样本有 256×8=2,048 个计算对，仅占全层行数约 0.191%。

下面的行号和来源卡分布由与当前选择器相同的 NumPy 抽样调用重新生成；收益读取已有真实八层回放，不在浏览器里重新优化。

查看全部 256 个样本行号
抽中哪些 token组的频次改变候选排名改变复制清单改变全量交换机会改变

抽样种子改变的是“观察到了哪些 token”，不是直接随机执行交换。比如种子 A 多看到 {e1,e2}，种子 B 多看到 {e5,e6}，有限槽位可能给了不同专家。后面的全量交换虽然按确定规则执行，可用专家清单已经不同，最终结果就可能不同。

相同种子还要配合同样的输入顺序、数组形状和软件实现，才能复现。现有逐层脚本为每层重新使用同一个种子；由于层的形状相同，抽到的行号相同，但每层这些行选择的专家可以不同。改变样本数量，也不保证大样本包含小样本，不能把它当成逐步追加的前缀。

样本能帮助判断常见模式，但会漏掉稀有组合、某些来源卡特有模式。全量交换可以阻止非法动作，却不能凭空补上抽样时没选中的专家副本。三个种子的结果接近，只是这份数据上的观察，不是对所有未来输入的精度保证。

05 / 不同的“组”怎样组成？

第一层：一个 token 在同一卡上的完整专家组

假设某 token 选择 [e1,e2,e3,e4,e5,e6,e7,e8]，当前执行卡依次是 [A,A,B,B,B,C,C,C]。它得到三组：

A：{e1,e2}，大小 2
B：{e3,e4,e5}，大小 3
C：{e6,e7,e8}，大小 3

这按当前执行卡划分，不按专家编号相邻关系，不按专家原属卡，也不把多个 token 合成一个组。为比较两个组是否相同，专家编号排好序后组成一条准确的列表；当前 CPU 代码不使用可能碰撞的短哈希值。

第二层：同类组的频率统计

对每个样本 token，查看每一对卡的两个移动方向。移动完整组的收益为：

收益 = 是否删除一个远端目的地 − 是否新增一个远端目的地

去掉负收益、以及剩余副本槽无论如何装不下的方向。同一个 token、同一对卡最多计一个方向：优先收益较高者；收益相同时按 token 行号和卡号算出固定规则选一个。这避免把同一个 token 当成自己的反向伙伴，但不同卡对之间仍可能重复估计同一个 token 的潜力。

统计类别的四个条件是 起点卡、终点卡、组大小、收益 0 或 1。例如某一类的示意频率：

A→B，大小 2，收益 1样本出现次数（教学数字）g=2 时
{e1,e2}40保留
{e5,e6}25保留
{e7,e8}9丢弃
{e9,e10}2丢弃

g=2 表示每个四条件类别保留两个最常见的专家组。同一方向、同一大小还能分别有两个收益 0 的组和两个收益 1 的组。它不表示只搬两个专家、不表示组大小等于 2，也不是整个方向只保留两个组。频次相同按专家编号列表排序，保证固定输入下结果可重现。

第三层：把正反方向的等大小组拼成候选

把 A→B 的大小 2 组，与 B→A 的大小 2 组组合。至少一边收益为 1，双方都为 0 的组合不考虑。每个候选问：“把这两组缺少的专家放到对面，需要多少个新槽？预计又能多实现几次有益交换？”

每一步选“新增预计通信收益 ÷ 新增槽数”最高的候选，更新驻留清单，再重新计算其他候选。因为刚复制的专家可能同时帮助其他组，不能只算当前这一对。没有正收益或没有足够槽位就停下，剩余槽不强制填满。已有均衡分配需要的专家副本始终保留。

这里估计的是样本里的匹配机会，不是最终执行指令；不同卡对可能竞争同一个 token。最终阶段从全部 token 重新产生提议，不能简单把样本收益乘以 134144/256 当作真实收益。

第四层：真正交换时的组，不必等于样本里的组

最后阶段只使用挑好的驻留清单，不要求 token 被抽中过，也不要求其专家组合进过候选排名。单计算对版本一次只提议移动一个任务。成组版本检查固定构造的 1、2、4 个任务，以及可以整体移动的完整旧卡组；每种大小按 top-k 原有顺序取可执行任务。没有枚举所有子集。

每个 token 仍只选一个提议。优先收益较大的；成组版本还轮换偏好的组大小，避免总挑最大组；其余按目标卡已有任务数和固定卡对规则打破平局。下一轮根据新的执行位置重算，所以可能形成不同的完整组。

06 / 复杂度：工作量究竟随什么增长？

“O(…)”表示规模变大时的工作量增长趋势，不是毫秒数。O(T) 表示 token 数翻倍，相关工作量大致翻倍；O(T²) 表示大致变成四倍。GPU 的并行、同步和内存读写会影响实际用时，不能把操作数量直接换成加速倍数。

符号解释当前数值
T，K，P=T×K全局 token 数、每 token 专家数、全部计算对数134,144；8；1,073,152
R，E，B卡数、全局专家数、每卡额外专家槽数8；352；8
m，g，I观察的 token 数；每类保留的组数；交换轮数256 或 4096；2 或 4；4
J所有计算对拥有的“其他合法执行卡”数量之和取决于副本分布，最多 P×(R−1)
Q，L正反组组成的候选数量；贪心选择成功轮数Q 随 g 增长；L 不超过 R×B=64

A. 选好驻留之后的交换阶段（不是原生 MoonEP 的 A 阶段）

这一步发生在“选择额外专家驻留”之后。即使前面用了 256 个样本，到了这里也已经拿到完整的驻留清单，所以称为“已有专家位置”。若不选择新副本，则直接使用原生起点必需的驻留清单进入同一步。这不是另一套独立算法，也不是原生 MoonEP 里叫作 A 的阶段。

对每个计算对，我们只检查已有该专家的其他卡，共计 J 次；不是检查它与所有其他 token 能否成对。匹配时用类别计数和顺序编号处理。

单计算对交换，I 轮： O( I × [ P + J + T×R + R² ] ) 最坏 J ≤ P×(R−1)。固定 R=8、K=8、I=4 后，随 T 线性增长。

公式中的 T×R 来自每个 token 建立当前目的卡占用计数；R² 来自双向类别匹配；P 包括扫描和写回。每轮最多一份提议/token，提议存储 O(T)，任务数组 O(P)。当前参考实现保留了成组分支共用的 R×R 小矩阵，即使单计算对模式也有这块小型存储，但它不随 T 同时复制 T 份。

成组交换，I 轮，当前参考代码的保守工作量上界： O( I × [ P + J + T×R² + 4×K×min(J, T×R²) + R²×K ] )

4×K×min(J,T×R²) 对应的具体代码：先为每个 token 建立“从 a 卡可移到 b 卡的任务列表”；然后遍历非空方向，为 1、2、4 或完整组这至多四种大小调用 _first_bits 从该 token 的任务中取出候选。每种构造至多处理 K 个位置，合计有效方向数不超过 J，也不超过 T×R²，所以得到该上界。它不是四轮：四轮已由外面的 I 表示。它也不是从专家组统计表一次处理一批 token。

每个 token 建立方向表需要 R² 的小表；最多为一个方向检查四种大小，每次从不超过 K 个任务里构造候选。大小 1、2、4 加完整组最多四种，不是 2 的 K 次方种。匹配名单按大小再分组，所以还有 R²×K 项。固定 8 卡、top-8 和四轮时仍然随 T 线性增长，但常数通常比单计算对版本大。

当前算法没有 O(T²) 的全 token 两两搜索。如果另写一种暴力算法，枚举任意两个 token 再试交换，才会有 token 数平方项。不能把那个假想算法当成当前“无采样”的基线。

B. 挑专家副本，本身分成三个成本

  1. 全量保底检查：扫描全部 P 个计算对，保留均衡起点已经需要的专家副本，检查是否超过 B。工作量 O(P+R×E)，抽样也不能省去。
  2. 观察 m 个 token：对每个 token 分组并检查各卡对，建立频率表。当前 Python 实现还会对组内专家排序，一个保守上界是 O(m×R²×K×log(K+1))。频率表中的不同记录数记为 U，U≤m×R×(R−1)/2；按频率排序挑前 g 个的保守上界为 O(K×U×log(U+1))。这些是源码级保守上界，不是紧确指令数；抽样库生成随机行号的开销另计。
  3. 从候选里反复选副本：此时已不再遍历 m 个原始样本，而是扫描保留下来的组和由它们组成的候选。它受 g、Q、L 和槽位预算影响。

为什么候选数量受 g 的平方影响？固定一对卡、固定一种大小，正向有至多 g 个收益 0 组、g 个收益 1 组，反向同样如此。总组合 4g²，去掉双方收益都为 0 的 g²，剩下至多 3g²：

Q ≤ 3 × [R×(R−1)/2] × K × g² 8 卡、top-8 时：g=4 → 最多 10,752 个；g=2 → 最多 2,688 个。

每次接受的候选至少新增一个专家槽，因此成功轮数 L≤R×B。每轮扫描所有候选，并重新计数同方向、同大小的可用组。按当前 Python 中元组包含查询也算成本，贪心部分可写一个保守上界：

O( (L+1) × [ R²×K²×g + Q×g×K² ] )

第一项是刷新已可执行组的计数；第二项是评估 Q 个候选。K² 是保守包含了“组内每个专家是否出现在新增专家列表里”的线性查询成本；使用位图或查表后可降低常数/这一因子。L+1 包括最后一次找不到可选候选的扫描。因此把 m 从 4096 降到 256，不会让整个选择阶段严格快 16 倍。候选排序、贪心和全量保底检查仍然存在。

C. 有采样和无采样，放在同一张表里

方案选副本阶段实际交换阶段
不选新副本，直接交换只做必需驻留的全量检查全部 T 个 token，I 轮
不抽样，用全量观察上述选择成本，令 m=T；若仍限制 g，候选 Q 仍受 g 限制全部 T 个 token，I 轮
抽样观察上述选择成本，令 m=256 或 4096；同时可以收紧 g仍是全部 T 个 token，I 轮

“不抽样”和“不限制候选组数”又是两件事。若 m=T、g=2，全量统计后仍只保留每类两个组；若把所有不同专家组都留下，正反组的组合数可能随不同组数量呈平方增长，贪心扫描也会更贵。本项目没有把这种无上限全枚举作为已实测性能基线。

总成本 = 原生均衡起点 + 全量驻留保底检查 + 观察/排序样本 + 候选贪心选择 + 全量交换 + 最终可执行计划构造。
采样主要缩减中间的观察与候选搜索，不能消除最后的全量处理，也不能消除原生 planner 的成本。

07 / 真实数据怎样变成仿真？

“仿真”在这里是对真实路由记录重新做分配并数通信，不是随机编造路由，也不是运行整个模型。数组的每个位置一直对应原来那个 token 的原来那个专家，不允许改专家选择来假装节省。

  1. 读原始记录。压缩包包含 8 个 rank×8 层，共 64 份记录，来自 iteration 4、microbatch 2，即一次迭代中的一个小批次。每份 [16768,8]，合成一层 [8,16768,8]。导出逐层 NPZ 文件（一种保存数组的压缩格式），保留来源卡和顺序。
  2. 确认输入边界。检查专家编号在 0～351、同一 token 的 8 个专家不重复。没有 gate 权重、完整序列与 padding 掩码、实际专家摆放记录。因此采用代码对应的连续编号原属布局；不能据此分析模型精度或 padding 对训练的影响。
  3. 建立均衡起点。用与原版一致的计数、配额、出现顺序逻辑，得到每个计算对的执行卡。每卡必须恰好执行 134,144 个计算对。原生 rt0 的真实 GPU 输出此前已与 CPU 语义模型逐项核对；rt2 的此次比较是 CPU 回放，不冒充新一轮原生 GPU 测量。
  4. 保留必需专家。把本卡原属专家和起点已使用的非本地专家加入驻留表。每卡总额外专家数≤8，否则起点不可行，不能继续作为有效方案。
  5. 选择额外专家。按给定种子抽 m 个完整 token，构造频率表、保留每类 g 个组、选择可互相匹配的候选，形成驻留清单。到此为止，任务执行卡没有改变。
  6. 全量交换四轮。使用驻留表，重新扫描全部 token。提议、分类、匹配、提交；每轮重新计算真实通信量，并检查收益与提议预测一致。
  7. 独立检查结果。每个计算对只有一个合法目标；目标卡有对应专家；每卡额外专家≤8；每卡负载与起点完全相等；原始 token—expert 关系不变；按 token 去重目的卡后重新计数。非法结果不能与合法结果一起汇总。
  8. 保存并对比。保存逐层执行卡和驻留表，保留参数、种子、输入文件校验值（用于确认文件未变化）。八层通信次数先求和，再计算降幅，不简单平均八个百分比。
通信次数 = 对每个 token 数出不同的远端目的卡数，再求和 通信降幅 = (原生 rt0 次数 − 优化后次数) / 原生 rt0 次数

这能检验“在固定路由下，计划是否可执行、负载是否均衡、token 数据要发多少份”。它没有复制真实权重，没有跑专家神经网络，也没有测网络拥堵、反向梯度或训练吞吐。要判断是否真正更快，还要把选择副本、执行计划构造、权重搬运和真实通信全部计入 GPU 实验。

08 / 已有结果，以及它们不能证明什么

下面是同一份 trace、每卡最多 8 个额外专家的已有记录；交换方案执行四轮，原生基线不执行额外交换。所有降幅相对原生 rt0，指标仅为去重远端 token 份数。256/4096 两种采样主对比均用种子 20261026。

方案八层远端 token 份数下降平均每卡活跃额外专家

256 的这一次结果稍好于 4096，不证明样本越少越好：样本和 g 同时改变，贪心选择路径也改变。三个 256 种子的成组结果是 24.98%、24.50%、24.54%；这不是置信区间，也没有跨迭代验证。

rt2 与采样方法拥有相同的“上限 8”，实际使用量却不同；采样方法接近用满槽位。两者差距不能全部归因于交换算法。rt2 还有按出现顺序分配没有完全实现本源保留的实现限制。

在同一份 256 样本驻留表下，单计算对交换下降 24.31%，成组下降 24.98%，相差约 0.67 个百分点。这是任务分组方式的可比实验；是否值得增加成组实现的时间，还需要对应 GPU 计时。

已有计时必须注明范围

  • 先前 CPU 选择副本时间：4096/g4 约 807 ms，256/g2 约 102 ms（已记录的对比中位数）。这是 Python/CPU 实现的观察，不是 GPU kernel 延迟，更不是 16 倍的保证。
  • 先前 8×H200 测试：固定 4096/g4 驻留表，四轮全局协调成组交换的八层中位延迟均值约 254.456 μs。只包含交换组件，不含生成驻留、最终地址编码、权重复制和专家计算；不能套到 256 样本或单计算对版本上。
  • “八卡协调”指每卡处理自己的来源 token，每轮交换小型类别计数以全局匹配；不是八卡各自独立交换。此前独立分片只有 15.55% 的通信降幅，全局协调保留约 24.62%。

当前最确定的判断

抽样是在减少挑副本的观察和搜索规模；按类别计数匹配已经避免了全 token 两两搜索。最后四轮仍然是全量工作。固定卡数、top-k、轮数和候选上限时，两种方式都可以随 token 数近似线性增长，区别主要在工作量常数、元数据、选择质量和同步成本。

下一步若要公平比较速度，应固定同一副本预算与输入，把“原生起点、选择副本、四轮交换、生成执行地址、权重预取、实际 token 通信”分别计时，再看总和。本节记录早期实验；2026-11-02 新增的单卡 H100 kernel 实测见后续报告。

09 / 新实验：先合并同类 token，再按数量成批交换

这是根据追问新增实现的 CPU 仿真，不是前面原有成组交换的另一种叫法。原有方法逐 token 产生一个提议；新方法对相同完整状态只评估代表，再按这一类有多少 token 分配交换数量。两种方法的选择规则不同，结果不要求相同。

为什么只记“{e1,e2} 在 A 有多少 token”还不够？

u、v 的 {e1,e2} 都在 A，也都来自 C。u 已经需要访问 B，v 尚不需要访问 B：同样把完整组从 A 移到 B，u 少发一份，v 只是把远端 A 换成 B，收益为零。如果 token 来自 A 或 B，收益还可能再次变化。只合并专家组会丢掉这些区别。

此外，一个 token 可能同时属于 A 上的组和 B 上的组。如果把两份组计数完全独立使用，就可能在同轮让同一个 token 做两个互相影响的交换，原先算好的收益不再可靠。

本次采用保守、可核验的合并条件：来源卡相同、完整专家集合相同、每个专家当前执行卡相同。把专家编号排序后比较，所以不因同一组的列顺序不同而拆开。我们称一类这样的 token 为“相同状态类”。它包含足够信息来算准确收益，也能维护一类还有多少 token 未使用。这个条件不是最粗的可合并条件，后续还有继续压缩的空间。

新算法具体怎样运行？

  1. 每轮开始，把全量 token 按完整状态合并，记录代表状态、数量，以及原始 token 属于哪一类。
  2. 遍历卡对，例如 A/B。每一类只检查一次：A 上的完整组能否移到 B，B 上的完整组能否移到 A。目标必须已有专家，收益不能为负；同一类在这个卡对只选择一个方向，优先正收益，再优先较小组，其他平局按固定规则处理。
  3. 按方向、完整组大小、收益汇总数量。不同专家组只要这些条件相同，在配平任务数时就可以合并计数，实际提交时仍保留各自专家信息。
  4. 选择两个方向各移动多少 token，使计算对总数相等。第一种对照只匹配相同组大小；第二种允许不同大小凑数。
  5. 将接受数量分给不同状态类。同一类有 100 个 token，可以先拿 30 个参与 A/B，剩余 70 个稍后参与其他卡对，并非整类必须一次搬完。每个 token 每轮至多移动一个完整组；本轮没有接受的才继续参与后续卡对。
  6. 所有数量决定好，再展开成原始 token 的具体分配。下一轮根据新分配重新合并，避免沿用已经分裂的旧状态。

不同大小怎么凑？

A → B：u 的 {e1,e2,e3}，1 个 token × 3 个任务，收益 1
B → A：v 的 {f1}，      1 个 token × 1 个任务，收益 0
B → A：w 的 {g1,g2}，   1 个 token × 2 个任务，收益 0

正向 3 个任务 = 反向 1 + 2 个任务
A 和 B 的计算量都不变；合计少发 1 份远端 token 数据。
两边的 token 数不必相同，必须相同的是计算对数。

这正是“找多个专家组来凑”的情况，本次已作为检查用例执行。对这种混合大小匹配，仅取两个名单数量的最小值已经不够。

新实现用一张整数任务量表求配平：对每个方向，计算“恰好移动 w 个计算对，最多能省几份通信”，w 从 0 到两个方向可供任务量的较小值 W。表中有每种组大小 1～K、收益 0/1 的数量上限。然后在两边都能实现的 w 中挑总收益最高者，再反推出各类该取几个 token。这叫动态规划，也就是复用已算好的较小问题答案，避免把所有数量组合重新枚举。代码使用滑动范围内保留最好候选的队列，将每种大小的表更新压到 O(W)。

这里的最优只针对当前卡对、已经产生的完整组候选和剩余数量。卡对按顺序处理，前面用掉的 token 后面不能再用；每轮会轮换卡对起点。它不是所有卡、所有任务的全局最优算法。

新方案的复杂度

G 表示本轮不同完整状态的数量，可能远小于 T，也可能几乎等于 T。Wab 表示卡对 a/b 可匹配的计算对数上界。它是任务数量，不是专家组类型数量。

一轮，按当前实现计： 构造与合并状态：O(T×K×log T) 的保守比较排序上界 按代表检查卡对、汇总和分发数量：O(G×R²×K) 仅同大小配平：O(R²×K) 不同大小混合配平：O( K × Σ卡对 W_ab ) 把数量展开成具体 token 分配：O(T×K + G×R²) 四轮就对各轮成本求和，因为 G 和 W 会变化。

这里合并使用 NumPy 的精确去重排序；专家集合的列排序只在开始时做一次。如果以后换成完整键校验的哈希表，合并可以争取平均 O(TK)，但那不是当前已经测过的 GPU 实现。内存主要是 O(TK + GR² + K×max W_ab)：原始数组、每状态的方向数量，以及整数配平的回溯表。

所以不能宣称“整体从 O(T) 降成 O(G)”。减少的是重复的方向评估；读输入、重新分组、展开结果仍需碰全量 token。混合大小配平还引入了依赖 W 的成本。本次 W 的最大值为 15,660；并非只扫描几种专家组就能完成所有精确凑数。

10 / 新实验：用共享专家子集替代完整状态类

这版不再把全体 token 按完整 8 专家状态排序合并，也不逐卡对遍历所有完整状态类。它先挑少量“专家子集＋移动方向”，为每个子集建立包含它的 token 名单，交换时只检查这些名单。它仍会读取名单中的 token，不能称为“只做一百多次计算”。

先把两个限制分开

h 是一组最多包含几个专家，本次测试 h=1 或 2；g 是每个“方向、子集大小、初始收益”类别保留几个最常见的候选。h=2 时同时考虑单专家和双专家子集。比如 {e1,e2} 就是一种共享子集，不要求 token 另外六个专家相同。g=0 在代码中表示不按候选数量截断，不表示零个候选。

从全量扫描变成名单查询

  1. 固定同一份 256/g2 选出的驻留表和原生 rt0 起点，不增加专家副本。
  2. 只在开始时完整统计：对于每个 token，枚举一个或两个在同一旧卡上的专家。仅保留目标卡能执行、初始收益非负的方向，按方向/大小/收益统计频次，留下前 g 个模板。这里使用全量初始路由统计，没有再次随机抽样。
  3. 建立“专家子集 → 包含它的 token 行号”索引。这就是一份查名单的表。只为入选子集保存名单：两次线性扫描先计数再填写，无需把所有子集记录排序。原型仍检查全量单/双专家组合，但不保存未入选项。
  4. 每轮按卡对读入选模板的名单。重新检查这两个专家当前是否都在旧卡、token 是否已使用过、是否真的能少访问一个远端卡。负收益丢弃。一个 token 若同时匹配多个模板，在当前卡对只留一个提议。
  5. 按方向、大小、真实收益汇总数量，用上一节的整数配平法选择双方相等的计算对总量。允许正向两个任务，反向两个单任务凑齐。
  6. 提交时标记已使用的 token，使它本轮不能再次参与其他卡对。名单可复用四轮，因为 token 选择的专家不变；执行卡和通信收益每轮、每次提议仍要重新检查。

例如所有含 {e1,e2} 的 token 都能进入同一份静态名单。但有的 token 已不在 A 执行这两个专家，有的仍留着其他任务在 A，有的已经需要访问 B。它们在这次 A→B 移动中的收益不同，因此还要按当前状态检查。仅凭名单长度就把全部 token 搬走，会算错收益。

入选方向模板在四轮内固定。初始不合法或不够热门、但后来变得有价值的模板可能被漏掉；这里的“全部模板”也只是全量保留初始有效的单/双专家模板，不等于无约束搜索所有可能交换。

复杂度具体减少在哪里？

定义 F 为所有非空候选统计类别数；C 为入选的方向子集模板数；Zi 为第 i 轮读取的名单条目总数。一个 token 可以出现在多个子集或方向中，因此 Z 可以比 T 大。T、K、R、E 的含义沿用前文。

本次 h≤2： 初始统计：O(T×K²×R) 的保守上界 筛选模板：O(F log F)，保留 C ≤ 2×h×R×(R−1)×g 构建选中子集索引：O(T×K² + E²)，保存入选名单而非全部组合 第 i 轮：O(K×Z_i + 2×Σ卡对 W_ab + T×K) 四轮总计 = 一次准备 + 四轮上述成本。

统计表用整数键；字典查询按平均常数时间估计。h=1 时枚举项可以从 K² 降到 K。E² 来自当前实现给单/双专家子集编码的密集索引表，专家数很大时可改稀疏表，但这不是本次已测实现。W_ab 是两方向可配平的任务量上限，h=2 时只有大小 1、2，因此整数表类型数是常数。

它消除了上一版每轮 O(TK log T) 的完整状态排序，以及 O(GR²K) 的全状态类卡对扫描，替换为入选子集的名单查询。不过固定候选数并不能让执行成本与 T 无关：热门子集可能命中很多 token，初始统计也仍然是全量。

当前 h2/g8 每层只有 118～142 个方向模板；平均保存约 602,243 条子集—token 关系，四轮累计读取约 10,781,235 条名单记录。很多记录会因 token 本轮已使用而快速跳过，但仍有访问开销。这正是“一百多个模板”不等于“一百多次工作”的原因。

同口径真实结果与 CPU 延迟

8 层完整 trace、相同原生 rt0 起点、相同专家驻留、每卡最多 8 个额外专家、四轮。所有通信降幅相对 rt0。每层三次交错顺序执行，取每层中位数，再对八层求平均；JIT（首次把程序编译成机器指令）提前完成，不计磁盘读写。延迟包含本算法的候选统计、筛选、索引构建和四轮交换；各方法共同的原生起点生成、驻留选择、最终通信地址生成不计入。

h2/g8 相比完整状态聚合约快 5 倍，同时通信降幅略有增加；但比原有逐 token 成组仍慢约 22%。这不是 GPU 延迟，不可与此前数百微秒的 H200 kernel 数据混用。只有三次本地 CPU 配对轮次，不作统计显著性或跨机器保证。

这份 trace 上 g=8、g=32 与不截断的模板集合已经相同，输出也逐项相同。所以不能把约五倍的 CPU 改善归功于 g=8 剪枝。主要变化是不用完整状态排序聚合、只考虑 1/2 专家子集、直接查名单。真正收紧到 g=2，候选为 103～119 个，延迟约降 4.6%，但通信降幅损失约 0.97 个百分点。

40 份最终方案全部通过独立检查：固定驻留不变、每卡副本不超过 8、每卡计算对精确 134,144、专家执行合法、去重通信重算和预测收益一致。新过滤索引与保留全部子集索引的初版，在所有方案上输出逐项一致。还检查了相同 {e1,e2} 在不同 token 上具有不同收益的构造例子。
