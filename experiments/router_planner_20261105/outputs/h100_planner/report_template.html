动画中的读取次数是示意结构，不是显存性能计数器。这个小例子有 6 个平铺模板，索引版先枚举 7 个自有子集，再经过驻留剪枝只查 3 个键；不能凭这个例子声称总运算一定少于 6 次。真实的 K=8 情形最多有 36 个自有子集，候选表则最多有 1,792 个有向模板。

“每个 token 读一次”限定在同时版的一轮提议阶段。总共运行四轮，上一轮修改执行位置后，下一轮需要重新读。模板统计准备、排序、提交、输出地址生成也会读写各自的数据。它不表示整次 planner 只访问 token 一次，更不表示所有访问都只落到显存一次。

03 / h、g、B：三个完全不同的限制

符号具体限制什么这次设置
h：共享子集大小上限一次模板允许包含多少个专家。例如 h=2 时考虑 {e1} 和 {e1,e2}，不考虑 {e1,e2,e3}。2
g：每类保留多少个模板按“移动方向、收益 0/1、子集大小 1/2”分开计数，每类取出现频率最高的 g 个，再去重。g 限制候选名单数量，不限制一张卡能放多少专家。8

“模板”是一条规则，例如“把目前在 A 的 {e1,e2} 移到 B”。统计表中它出现得多，只说明很多 token 可能用得到它。每轮仍要检查当前执行位置、B 是否拥有所需专家、是否会增加远端数据份数，并重新决定接受哪些 token。

04 / 先生成均衡计划，再做保持负载的交换

计划执行位置改变，不等于 token 已经传输。原始来源卡是本层输入 token 所在的卡；计划执行卡是准备让某个专家任务在哪里计算。规划阶段一直保留原始来源，修改的是任务的执行计划。当前成组交换测试没有先发一轮 token，再把收到的 token 重新交换。

原始路由与来源卡MoonEP rt0 均衡草案按来源＋草案选择专家副本成组等量交换修改草案最终执行地址与通信清单

每张卡在草案中已经有同样多的专家计算任务。成组交换要求 A→B 和 B→A 搬动同样多的任务，所以它保持已有均衡，并不负责把任意不均衡输入变成均衡输入。只有最终计划确定之后，实际系统才按它发送 token、准备专家权重；两类通信的调度可以分开，专家计算前需要准备好。本次单卡实验只测规划，没有执行这些实际通信。

当前实现边界：副本选择是此前 CPU 回放生成的固定输入，既没有集成到这次 GPU 交换 kernel，也没有算进表中的交换或起点＋交换＋输出延迟。实际权重拉取也未计时。原包的计划接口本身不发送 token；集成优化时应在真实 dispatch 之前修改计划，不能先完整 dispatch 再把这份规划收益当成节省。

“这张卡的 token”指原始来源卡，不是计划执行卡。一个 token 的 8 个任务即使分散到几张卡，原始来源卡保留的完整路由行仍能看到全部专家及其执行位置，由它统一提出本轮的一条交换建议。扫描的是专家编号与执行位置等元数据，不是 token 的隐藏向量。当前单卡 H100 测试把 8 份来源数据展平成一个数组；8 线程版本的八卡协调接口尚未完成八卡实测。这个分片说明仅针对当前成组交换实现，不概括原生 MoonEP 所有子 kernel。

展开：256 个样本怎样变成副本清单

先全量统计起始分配已经要求哪些专家在哪张卡执行。每卡保留自己的原属专家和这些必需副本；必需副本也占“最多 8 个额外专家”的预算。剩余槽位才参与下面的选择，不能先把已有合法执行位置删除。

从全层 134,144 行均匀、不放回地抽 256 行，每行保留全部 8 个专家及当前执行位置。对抽到的 token，把当前计划在同一张执行卡的任务合成一组。例如某行在 A 卡上的全部任务是 {e1,e2}，便考察把这一整组移到 B 是否能减少远端份数；如果所需新增副本已超过 B 的剩余预算，先剔除。每个样本、每对卡最多选择一个方向，避免把同一个样本同时当作自己的反向伙伴。

源码的“保留 2 组”是每个完整类别：方向×大小×收益，分别保留出现最多的两种专家组合。同方向、同大小如果收益 0 和收益 1 都有候选，合起来最多有 4 组。之后把反方向、相同大小的候选组合成一个方案：B 需要补齐 A→B 组的专家，A 需要补齐 B→A 组的专家。

每次选择“新增可匹配的样本通信收益 ÷ 新增专家槽位数”最好的方案，更新两张卡的驻留表和剩余预算，再重算候选。已经存在的专家不重复收费；一个新增专家也可能同时让其他保留组合变得可用。八张卡联合选择，每卡始终不超过 8 个额外专家；没有正收益可选时结束，允许剩余槽位空着。

这里直接使用样本频数，没有乘 134,144/256 外推成全量次数。不同卡对仍可能用到重叠的样本，因此这是候选价值的估计，不是可立即提交的交换清单，也不保证全局最优。最后真正执行哪些交换，要由全量阶段重新判定。

已有三种抽样种子 20261026、20261027、20261028 的八层最终远端份数下降分别为 24.9794%、24.5005%、24.5397%。总体相差约 0.48 个百分点，但单层波动更大：第 7 层分别为 26.4472%、32.3976%、28.8764%，最大相差约 5.95 个百分点。因此不能只凭八层总数相近就断言采样稳定，也不能把三次结果当成一般精度保证或置信区间。全量交换会阻止非法执行，但不能补回采样时没有选中的专家副本。

展开：两组各含几个专家？哪些双向方案参与比较？

“保留两组”限制组合种类数，不限制每组只有两个专家。每个样本在某张计划执行卡上的完整组，可以含 1～8 个专家。大小 1、2、3……8 分别统计，收益 0、1 也分别统计，各类别保留两个组合。因此大小 3 的类别可以同时保留 {e1,e2,e3} 和 {e4,e5,e6}。

对同一卡对、同一大小，将两个方向保留的组合逐一配对，排除双方收益都是 0 的方案。不是只把第一名和第一名配对，也不是把前两名全部复制。每方向两种收益各最多两组，因此最多 4×4 个组合，排除 0+0 后每卡对、每大小最多 12 个方案。

代码计算“假设新增副本后的可匹配收益 − 当前可匹配收益”，再除以真正缺少的副本数；比值相同优先增量更大，再优先副本更少，最后按固定方案顺序。它重算当前卡对、当前大小下的所有保留组，因为一个新专家可能补齐其他组；这仍是样本上的估计，不是全体 token 的联合最优解。

全量扫描之后的两张表

非负收益只是候选资格，不是所有候选都进入计数表。每个 token 比较全部方向和候选大小后，只提交一个最佳提议；汇总的是这些唯一提议。若该提议没有获得反向配额，本轮不再提交第二名。下一轮才重新计算。这样避免一个 token 的多条重叠提议被同时接受，但也可能漏掉原本可匹配的次优机会。

“1、2、4”各取原路由顺序下前几个可搬任务，不枚举所有同大小组合；“全部”指这个 token 当前计划在搬出卡上的全部任务，未必是全部 8 个。收益 1 优先于收益 0；同收益再按随 token 与轮次变化的大小优先级、目标卡已有任务数和方向规则选择，因而不是始终优先最大组。

每个 token 先读自己的 8 个任务，检查 56 个有效移动方向，每方向考虑前 1、2、4 个可搬任务和原卡上的全部任务，只留下一个最佳合法提议。具体专家组合的可执行性已经在这一步检查；匹配阶段只需要知道方向、任务数量和通信收益。

八卡接口每轮汇集各卡的 1,152 个 32 位整数：一张卡的输入计数是 4,608 字节，汇集后每卡得到的计数数组是 36 KiB。这是数组大小；实际网络传输字节数和延迟取决于通信实现，不能直接等同于这两个数。

全局总数决定每类接受多少条；各来源卡之前的累计数决定这张卡的提议排在全局第几位。例如这一类全局收前 100 条，前面的来源卡已有 70 条，本卡只有前 30 条可进入。各卡内部按 token 顺序排列，所以不必把全部 token 提议表传到一张卡集中选择。

以下是手写示例。固定 A、B 两张卡，所有提议大小均为 2；“条数”指 token 提议数量。

双方各接受 100 条、每条搬 2 个任务，因此每个方向都搬 200 个任务，两张卡的任务总量保持不变。远端份数减少 100＋60=160。剩余可配的都是收益 0 的组合，本版不会为了零总收益继续交换。

如果希望副本选择阶段也查看全部 token，当前 CPU 函数可以把 sample_tokens 设成 N=134,144，按相同规则扫描全部数据。这会消除抽样遗漏，但仍保留每类别前 2 组和贪心选择，并不因此成为全局最优算法。这个全量副本选择的 GPU 版本、以及八卡分布式统计完整专家组合频数后再选副本的流程，目前尚未实现。

分布式实现必须先按同一专家组合正确合并全局频数，再找全局前 2 组。不能每卡只保留本地前 2 组再合并，就称为精确的全局前 2 组：某种组合可能在每卡都排第三，合计后却应当第一。现有八卡计数汇集接口解决的是固定驻留后的交换配额，不等于已经实现分布式副本选择。

共享子集与完整聚合：一组两个任务，也能换两组各一个任务

下面的混合大小匹配属于共享子集与完整状态聚合。报告中的“8 线程成组交换”采用相同大小的反向提议配对，不把一个大小 2 的提议与两个大小 1 的提议匹配。

等量条件是计算对数量相等，不要求 token 数或专家组数相等。在动画最后，A 交出 u 的两项任务；B 交回 v、w 各一项任务。A、B 都净增零项计算，所以负载不会变化。

为什么 u 的收益可以是 0？u 的 e3 仍留在 A，e7 原本就在 B。把 e1、e2 移到 B 后，u 还是访问 A、B 两张远端卡，份数不变。不过它提供两个反向交换名额，可以让另外两个 token 各省一份通信。
为什么不能接收三条重叠提议？{e1} 与 {e1,e2} 共用 e1。若同时接收，e1 会被安排两次。当前同时版在一轮里只为 u 产生一条提议，接受时整条提交，自然避免这个冲突。

匹配程序实际算什么

先把每一对卡的提议按“方向 × 收益 × 大小”计数。例如 A→B 有 5 个大小 1、收益 1 的提议，还有 3 个大小 2、收益 0 的提议。先求双方都可能移动的最大计算对数 W，再逐一考虑移动 0、1、…、W 个任务时，能获得多少收益。

共享子集当前只有大小 1、2。代码用一个固定次数的整数计算，求给定移动量 w下最好的接收数量，然后把不同 w 并行比较。它仍会比较多个 w；“固定次数”只针对一个 w，不代表整张配额表是常数复杂度。收益相同时选择较小移动量，并保留旧版动态规划的数量选择规则。

完整状态聚合允许大小 1～8，不能直接套用这个双大小公式。它保留“动态规划”：逐类加入可选组，在每个确切移动量上保存目前最好的收益。当前 GPU 实现有明显的顺序依赖，是需要结合实测分析的成本。

同时版改变了处理顺序：旧版先完成一对卡，再处理下一对；新版先让所有 token 各选一条，再同时匹配。因此，“旧顺序版”和“同时版”的通信收益可能不同。平铺同时版与索引同时版保持同一规则，GPU 校验确认二者输出一致。

步骤准确含义与需要纠正的地方计算工作量工作区／必要空间
0. 获得起始分配调用 rt0 planner 生成均衡的初始执行位置；此时没有做真实 token 分发。原包多卡实现与当前单 H100 语义移植版需要分别计算。原包所有卡合计：O(N(1+log R)+R²)。

单 H100 移植版：O(N+R²)。
1. 保留必需专家全量统计 counts[执行卡,专家]。保留原属专家和起始分配要求的副本。这是一张“必须能够执行”的计划表，不代表专家权重已物理复制到位。CPU 全局：O(N+R)表本体 O(R)；当前 NumPy 表达式还产生长度 NK 的索引等临时数组，因此峰值工作区为 O(N+R)。
2. 抽样全层均匀、不放回抽 d 个完整 token，再按原行号排序。不是每卡各抽 d 个。稀疏抽样路径加排序：O(d log(d+1))保存 d 个样本索引为 O(d)；NumPy 在 d 较大时可能选择建立长度 N 临时数组的路径，不能对所有 d 保证只有 O(d) 峰值空间。
3. 统计组、筛选候选、构造反向组合对样本按当前执行卡组成完整任务组；方向指“执行位置旧卡→新卡”，不一定是原始来源卡向外发送。每个“方向×大小×收益”保留前 2 种专家组，再与反方向同大小组联合配对。这里还不复制专家。当前 CPU 总上界：O(dR² log(d+1))。代码先将每个类别的完整频数表排序，再取前 2，不能把它写成只看 2 项。O(dR²)，保留样本组合频数、筛选结果和候选组合。
4. 选择驻留方案全局反复比较“新增可匹配收益／新增槽位成本”，每选中一个方案都更新驻留并重新计算候选增益。不是每对卡各选一次，也不是把频数最高的专家直接复制。实际选择 I 次时：O((I+1)R²)；I≤RB，固定 B 后最坏为 O(R³)。当前函数还保留步骤 3 的表，合计 O(dR²+R)。不能只计算最后那张布尔驻留表。
5. 执行一轮全量成组交换每 token 最多一个提议；收益 0 的提议可以参与，但最后只接受正收益组合，如 1+0、1+1，不接受 0+0。如果最佳提议未匹配，不自动退回第二名。八卡接口每卡：O((N/R)(R+R²+p)+R³)。
单 H100、全量 N：O(N(R+R²+p)+R²)。		八卡接口每卡额外工作区：O(N/R+R³+L)；单 H100：O(N+R²+L)。L 仅来自逐轮统计，主要数组重复使用。
6. 汇总全部卡的工作这是步骤 5 的计数，不是额外扫描。单卡枚举方向为 (N/R)R²；全部卡合计 NR²。若做 L 轮，每轮更新执行位置后重新提议、匹配。全部卡一轮的工作量为步骤 5 单卡工作量乘 R；做 L 轮再乘 L。步骤 0—4 不因此重复 L 次。主要临时数组不乘 L；只有保留每轮统计的少量数组为 O(L)。

用一个小例子区分“组大小”和“新增副本数”：卡 0 已有 e1、e7、e8，卡 1 已有 e1、e2、e7。样本中，100 个来自卡 0 的 token 各有 {e1,e2} 两项任务安排在卡 1；30 个来自卡 1 的 token 各有 {e7,e8} 两项任务安排在卡 0。给卡 0 补 e2、给卡 1 补 e8 后，两个方向都能把完整两任务组移回来源卡。组大小是 2，新增副本却是每边各 1 个。

两个方向能匹配的样本数为 min(100,30)=30；每对减少 1+1=2 份远端发送，所以估计收益是 60，除以 2 个新增副本，得 30 份／副本。不能将两边 100+30=130 都算成收益。实际代码会比较新增专家前后的可匹配收益之差，并把同方向、同大小中其他被顺便启用的保留组也算进去。样本之间跨卡对的重叠仍可能存在，因此此分数是选副本的估计，最终全量扫描才决定真实交换。

步骤 4 的 I 是实际接受的副本方案数量；每次至少占用一个此前未用的额外槽位，因此 I≤RB。这里的 O(R³) 是预算限制给出的最坏上界，不表示每次都把所有槽位填满。

当前 8 线程成组交换使用原始来源卡分片：每卡处理 N/R=16,768 行，每行能看到该 token 的全部 8 个专家及其执行位置。每行有 56 个有效方向，因此一轮每卡有 939,008 个方向检查位置，八卡合计 7,512,064 个；不可搬的方向会提前跳过。每个方向最多考虑前 1、2、4 个可搬任务和原卡上的全部任务。

八卡接口中的 R³ 来自当前实现把 R 张来源卡的 O(R²K) 计数表全部收集到每张卡，再逐来源卡累加；不是 token 两两匹配产生的。当前 H100 数据是在一张物理卡上处理全部 N 行，只有一份计数表，因此这一项是 R²。跨卡汇集还会产生通信，其延迟不能由上述计算工作量直接推算；本次单 H100 延迟也没有测到八卡汇集成本。

展开：保留 K、E、B、g 后，各项具体从哪里来

步骤 1：全量计数与表初始化为 O(NK+RE)；表本身 O(RE)，但当前 NumPy 先生成所有计算对的索引等临时数组，峰值工作区为 O(NK+RE)。固定 K、E 才得到主表中的 O(N+R)。

步骤 3：为一个样本检查卡对需要 R² 个循环位置；同一旧卡的完整专家组会对不同目标卡重新排序、判断，合计建表上界为 O(d[R²+RK log(K+1)])。这是当前 CPU 源码对“完整旧卡组”的处理，不是枚举 2K 个任意子集。

令 H 为频数表中不同记录的数量。每个样本、每对无序卡最多记录一个方向，所以 H≤dR(R−1)/2。每个完整类别内至多有 d 种组合，代码完整排序的比较工作上界为 O(KH log(d+1))；K 来自最坏情况下对专家元组的比较。固定 K、g 后，步骤 3 总上界就是 O(dR² log(d+1))。

令 J 为筛选后保留的组数、P 为反向候选方案数，则 J≤2gR(R−1)K；排除收益 0+0 后，P≤3g²K·R(R−1)/2。本次 R=8、K=8、g=2，P 的上界是 2,688，不是每次一定达到这个数。

步骤 4：每次选择前，先检查已保留的组是否被当前驻留启用，工作量 O(KJ)；再重算所有候选方案。当前实现对元组执行 e in add_a 一类成员判断，最坏需 O(K)，因此每轮候选评估为 O(PgK²)。总体为 O((I+1)[KJ+PgK²])；固定 K、g 后为 O((I+1)R²)。函数尚未释放前面的频数表，空间为 O(dR²+RE+RB)，其中 K、g 已按固定常数处理。

步骤 5：令每张卡的本地 token 数为 n=N/R。提议阶段为 O(n(KR+R²))；整数基数排序为 O(pn)；本地类别计数和配额为 O(R²K)；R 份计数表的汇总工作与存储均为 O(R³K)；写回上界为 O(nK)。因此当前八卡接口每卡每轮合计：

O(n(KR+R²+p) + R³K)，其中 n=N/R。 额外工作区：O(n + R³K + E + L)。 把本地 routes、owner 和 support 也计入：O(nK + RE + R³K + L)。 单 H100：将 n 换成 N，将 R³K 换成 R²K。

“位掩码”是用整数的不同二进制位表示任务集合；当前集合装得进一个整数，所以提议阶段后续的交集与计数无需再逐专家扫描。排序只处理类别编号的 11 个二进制位，p 是本实现固定的小常数；不能另乘一次 K，也不能把它自动写成比较排序的 N log N。当前 kernel 硬编码 R=K=8，改变 R、K 后需要重新设计相应表示和代码；这些展开式用于解释当前成本来源。

步骤 0 的两种实现：原包 rt0 planner 利用有序配额边界定位执行卡，工作量中的 log R 与这类查找相关；本次单 H100 语义移植代码按目的卡顺序扫描，因此该项为 R。两者并非同一个 kernel，不能用移植版的计时替代原包多卡 planner 延迟。这里不包含真正的 token 分发、专家计算或权重复制。

最终输出还需一步：交换修改了任务执行位置后，需要重新生成物理专家槽、执行地址及去重发送元数据，不能继续使用第 0 步的旧地址。当前固定参数的单卡输出构建随 NK 线性增长；这一步不重新做负载均衡。之后才进入真实的专家权重复制与 token 分发。

固定实际 R=8、K=8 和排序位宽后，步骤 5 的工作量随本地 token 数近似线性；固定轮数 L 后仍是线性。减少轮数会减少重复工作，但 GPU 延迟还受并行调度、访存、启动和通信影响，不能将工作量简单除以 8 个线程，或据此断言一定缩短多少毫秒。

成组交换：R、K 分别花在哪一步？

这里讨论“每个 token 由 8 个线程协作”的成组交换。它的组是同一个 token 的若干专家计算任务。先固定专家驻留位置，每轮为每个 token 最多选一条搬运提议，再按相反方向、相同任务数量匹配；16 线程版与 8 线程版遵循同一规则。

N 是一层全部 token 数，本次为 134,144；K 是每 token 选中的专家数，本次为 8；R 是逻辑卡数，本次为 8；L 是交换轮数；p 是整数排序扫描数据的趟数。下面另用 Ul 表示第 l 轮真正改写执行位置的计算对数量，一个计算对就是“一个 token 交给一个专家算一次”，所以 0≤Ul≤NK。

步骤一轮工作量这个乘数从哪里来
1. 建立当前位置和可执行位置的小表O(NKR)每个 token 的 K 个专家任务，都要判断它对应 R 张卡中的哪些卡。一个 token 有 8 个专家、8 张卡时，共有 8×8 个“专家任务／卡”检查位置。
2. 选择搬运提议O(4NR²)每 token 检查 R² 个方向位置；自身到自身跳过，本次有 56 个有效有向卡对。每方向最多考虑前 1、2、4 个可搬任务和原卡上的全部任务。每个候选复用小表做整数位运算。
3. 按类别整理提议、决定接受数量O(pN + R²K)N 条记录按类别排序；计数和接受数量按“方向 × 收益 × 搬几个任务”保存。最后一项的大小范围是 1…K，因此有 K，不是每个 token 再与 K 个 token 比较。
4. 写回被接受的执行位置O(N + Ul)
上界 O(NK)		扫描 N 条提议，跳过未接受的；接受的提议搬几个任务，就改写几个位置。一个 token 最多有 K 个位置，因而最坏上界有 K。

第一步乘 R，表示检查工作量，不表示把 token 从显存重复读取 R 遍。当前 kernel 的 8 个线程先各读一个专家和执行位置，再循环检查 8 张卡。每张卡的“哪些任务现在归我”和“哪些任务我能执行”压成一个整数：每一位表示一个专家任务是否在集合中。后续方向比较复用这些整数，使用线程间交换与位运算。这样减少重复读取，但检查逻辑本身仍存在；这也不是缓存命中率或显存事务的实测结论。

第三步为什么不是只有 1、2、4 三种大小？因为还有“把原卡上的任务全部搬走”这个候选。例如某个 token 有 3 个任务在 A，且 B 都能执行，那么大小 3 的全组可以参加；5、6、7、8 也同理。因此配额表按 1…K 预留类别。本次只需给 28 对卡×8 种大小分别算数量，共 224 项；每项是固定次数的整数计算。它不做全体 token 两两比较，也不搜索“2 个任务与 1+1 个任务”的混合配对。

例如 A→B 有 100 条大小 2、收益 1 的提议，B→A 有 120 条大小 2、收益 1 的提议，直接接受双方各 100 条即可，不需要做 100×120 次比较。排序保证同一类别里按原 token 顺序选取。这里的排序只处理类别编号的 11 个二进制位，不对 token 编号逐项比较；当前 p 是固定的小常数，所以是 O(pN)，不写成比较排序的 O(N log N)。

每轮：O(NKR + 4NR² + pN + R²K + N + U_l) L 轮最坏上界：O(L · [N(KR + R² + p) + R²K]) 若把一次驻留位图准备也计入，再加 O(RE)，E=352 是专家总数。 当前 R=K=8、p 固定：O(LN)；L 也固定时：O(N)。

上述是总工作量，不是把每一步串行执行所需的时间。GPU 可以让许多 token 同时处理，但不能据此把整个式子直接除以 8。当前实现把 R、K 写死为 8，且集合装在单个整数中；不能不改实现就将此式外推到任意大的 R、K。16→8 线程改变执行效率和常数，不改变复杂度阶数。第四步实际只改 Ul 项，比直接写 NK 更能解释后几轮搬得少时的成本。

完整状态聚合：合并有成本，混合匹配也有成本

总工作量 = O( Σ[l=1…L] { NK² + KN log N // 排好每 token 专家、按完整状态比较排序 + P(N + K·G_l) // 启动全长数组处理、每卡对扫描状态类与计数 + K·Σ[a<b] W_l,ab // 大小 1…K 的混合数量匹配 + NR² + NK // 按方向展开接收数量，写回计算对 })

保存的真实回放中，八层 × 四轮共 32 个 G 值的平均为 50,885.41 类，约为 N 的 37.93%；最少 15,226 类，最多 126,986 类。此前的 126,984 是第 0 层首轮的具体值，不是所有层固定的类数。见逐层完整状态统计。

这里确实有 N log N：使用 Thrust 按完整状态进行比较排序，一次状态比较最多查看 K 个专家及其执行位置。即使相同 token 很多，程序也要先整理全量输入，才知道哪些可以合并。实际代码为安全分配长度 N 的工作区，部分 kernel 也按 N 启动，因此不能把所有 N 都换成 G。

聚合 AoS 版读取某一类的代表 token；SoA 版先把代表信息转成按字段连续排列的表，随后 28 对卡复用。两者算法和输出相同，复杂度相同；区别是数据如何排放、读取是否容易合并。

共享子集：三种执行方式的差别

实现四轮交换工作量上界消除了什么，还留下什么
保持旧顺序 exactO(Σ_l [NK(P+M) + PpN + PN + Σ_ab W_l,ab])同一对卡内一次读 token、复用模板；换卡对仍重新检查。四轮有 4×28=112 次排序/配额/提交。
平铺同时版 flatO(Σ_l [NMK + pN + NK + Σ_ab W_l,ab + R²])一轮加载 token 一次，遍历全部模板；四轮只做 4 次排序/配额/提交。最坏情况下 NMK 比较仍存在。
索引同时版 indexedO(L [NK²R + pN + NK + R²])枚举 token 自己的子集并查表，去掉 M 因子。与 flat 同规则、同输出。每轮每 token 最多提出一项，因此所有卡对的 ΣW≤N。

对子集同时版，最多 K + K(K−1)/2 = 36 个单/双专家子集。双专家必须当前在同一执行卡；目标卡还必须同时有这些专家，筛掉后才查索引。上界是 36×7 个实际目的卡查表候选，通常更少。它仍然会做“生成自己子集”的工作，不能说每 token 的算法变成零比较。

共享子集的排序采用 CUB 整数基数排序，写成 pN；完整聚合的完整状态比较排序写成 KN log N。两种排序不要合并成同一个 O(N log N)，也不要把它们都当作无成本。

准备模板也必须计入完整范围

共享准备：O(NK²R + R²C²g + P(hg)² + RE + NK) 索引版额外建表：O(R²C² + M)

第一项来自遍历 token 的单/双专家组合并统计可移动方向；第二项来自扫描计数表、维护每类前 g 个候选；第三项来自候选去重和小表排序；E=352 是专家总数。索引额外成本包括清空查找表、写入选中的模板。这里不包括选择新的专家驻留位置，各版本都使用相同的保存结果。

06 / GPU 层面具体改了什么

修改人话解释收益边界
按字段连续存放，合并访存把“token0 的 8 个专家、token1 的 8 个专家”转成“所有 token 的第 1 个专家、所有 token 的第 2 个专家”。相邻线程读同一字段时，地址也相邻，GPU 容易一次取回一整段。减少访存浪费；转换本身要读写 NK 项。完整聚合 SoA 和共享子集都计入各自需要的转换。
模板放进共享内存一小队线程先把模板表放到芯片上的公共临时区域，再各自处理 token。每个 token 的专家和执行位置尽量留在线程的小型临时存储中复用。平铺版仍遍历模板；缓存位置改变不等于算法候选数减少。编译器是否溢出到其他存储还会影响速度。
计数只用目标卡的驻留编号全局有 352 个专家，但目标卡最多只有 52 个可执行专家。用这 52 个本地编号做单/双专家计数，然后恢复全局编号比较频率相同的候选。计数工作区从 127,238,144 字节缩到 2,822,144 字节，保持原本的同分顺序。不是删除合法候选。
合并相同计数更新同一批 32 个线程若同时给同一个计数格加一，由其中一个线程一次加总，减少多人争抢同一个格子。仅对同时遇到相同格子的线程有效；不同格子仍分别更新。
子集直接查表索引由 GPU 已选出的模板建立，总计 705,536 字节。表里记的是模板原来在名单中的顺序，同分时按原顺序决定。不再扫描无关模板。查表地址可能不连续，所以不能只凭运算次数推断延迟。
大小 1/2 的配额公式把一般动态规划换成给定移动量下的固定次数整数计算，很多不同移动量可以并行计算。仅适用于当前大小 1、2；不能直接用于完整聚合的大小 1～8。
768 类起始位置并行计算原先一个线程逐项累加，现在 256 个线程分三段一起算每类之前共有多少提议；每段再加上前段总量。整数前缀与原版完全相同。独立第 0 层诊断由约 29.23 降至 2.44 μs／次，不把诊断数替代无 profiler 的正式计时。
成组交换 16→8 线程协作旧版用 16 个协作线程处理一行，只有 8 个线程加载专家，但 16 个线程都会枚举交换方向。新版用 8 个线程，一次 warp 处理 4 行，保持原算法规则。加载阶段少了空载线程，但每线程的方向枚举从 4 次增加到 8 次；不能说旧版一半线程全程空闲。速度以实测为准。

“一批 32 个线程”在 CUDA 中叫 warp；“共享内存”是同一线程块能共同使用的芯片内存；“合并访存”指把相邻线程对相邻地址的请求合成较少的内存事务。它们解决的是硬件执行成本，不改变专家副本预算或负载守恒条件。

__SCOPE_TABLE__
输入 trace 与固定驻留起始均衡分配GPU 统计并准备模板四轮交换生成物理地址和去重输出

交换段从已有分配开始；共享子集在这个范围里可以使用已准备的模板。准备＋交换把 GPU 统计、筛选、排布转换，以及索引版建表算进去。起始分配＋准备／交换＋输出再加上起始 owner 和最终可执行输出的构造。

输出构造包括：专家在目标卡的物理槽、按专家连续排列的行号、对齐补空位置、来源信息、以及“同一 token 发到同一目的卡只记一次”的目的地址标记。这些是本次紧凑物理槽格式的元数据；已与独立 PyTorch 实现逐项核对。它尚不是可直接替换 MoonEP dispatch 接口的成品，也没有集成到实际数据发送路径。

所有这些范围都排除了：选择专家驻留方案、真正复制专家权重、发送 token、合并结果、专家矩阵计算，以及真实八卡之间的同步。因此，它们是 planner 部件的测量，不是完整 MoE 层或训练端到端测量。
__TIMING_NOTES__

单卡八逻辑 rank，与原生 MoonEP 怎么比较

主表里的 MoonEP R8 port，是把原 rt0 的分配语义移植到单卡：它处理同一份八来源输入，产生同样的起始 owner；使用单卡排序和多个 kernel。它没有真实 NVLink 数据收集、跨卡远端写入和八卡屏障。所以它是相同硬件上的语义基线，不能叫“原生 MoonEP 八卡耗时”，也不能当作原生八卡的严格上界或下界。

计划中的原生 R1 对照只使用一个 rank，将八个来源拼成单来源，所有专家本地可用。此次实际运行在 NVLink multicast 初始化时失败，尚未执行到 planner kernel，因此没有原生 kernel 延迟。即使 R1 能运行，其工作任务也与 R8 不同，不能相除得出加速倍数。真正的原生 R8 延迟需要八张物理 GPU。

__NATIVE__

普通执行（eager）由 CPU 逐次发起 GPU 操作；CUDA Graph 先记录固定执行流程，再整体重放。GPU 事件计时测相应设备时间线区间；同步墙钟还覆盖 CPU 发起与等待。当前完整聚合使用 Thrust 排序中的分配及同步，未纳入 Graph 版本，应该用各方案都存在的普通执行行比较。
