扫描优化确实降低了交换组件成本

kernel 指一次在 GPU 上执行的计算程序。原路径为每个 token（输入的一条数据）的交换提议排序。新路径先保存每个 token 哪些任务能在每张卡执行，用一个整数的二进制位表示任务集合；四轮交换复用这些小表。随后按固定大小的数据块统计各类提议数量，把前面各块的数量相加，就知道本块从哪个名额开始，保留原先的稳定顺序。

这同时减少重复读取、重复判断和全量排序。当前仍为每个 token 最多保留一个提议，再按反方向、同样任务数匹配；没有改变这批输入的最终结果。

提前传权重：执行顺序与实际重叠

专家副本表确定→ 独立执行流传专家同时继续全量 token 规划→ token 计划确定即发 token→ 两边完成后才能算专家

执行流是 GPU 的一条有序任务队列。MoonEP 适配器用独立队列提前复制专家权重，token 通信等待自己的地址计划，不等待权重；真正的专家计算必须等待两边都完成。权重表、物理槽和源权重版本在使用期间保持稳定。

本轮同时测试 MoonEP 和当前算法的提前传输方式。当前算法提前传输的平均用时为 13.111 ms，串行为 13.018 ms。提前发起不保证更快：两类传输仍共享 NVLink、显存带宽和 GPU 执行资源。具体瓶颈需要性能分析，不能仅凭这组总时间指定原因。

原包 MoonEP 的 planner 把内部步骤合在一个 kernel 内，外部只能在整个 planner 完成后拿到事件。当前算法的专家表在全量交换前已确定，因此可在这个位置发起预取。若要进一步在原生 planner 内部更早开始，需要额外拆分或发布就绪信号，不能把目前接口说成已经做到。

DeepEP 的版本与验证范围

目标环境为 CUDA 13.0、NCCL 2.28.9。兼容测试选择官方 DeepEP v1.2.1，固定版本 9af0e0d0e74f3577af1979c9b9e1ac2cad0104ee。专家先转换为“目标卡＋本地物理槽”的编号，再交给原有 dispatch（发送 token）和 combine（返回并合并结果）。该版本的接收数据按 token／目标卡去重，真实专家矩阵计算还需要额外整理数据，不能直接用原始通信时间对比 MoonEP 的完整专家布局。

v1 的两个本地补丁仅调整构建：显式关闭本轮不用的跨机依赖，并补齐 GPU 设备代码的链接步骤；没有改通信 kernel，也没有替换用户现有 CUDA／NCCL 环境。补丁文件和原始指纹均保留。构建、导入、两卡正确性是不同阶段，只有实际结果文件能证明对应阶段通过。

导入成功后的首次通信仍被上游形状限制拒绝：每卡有 176 个原专家和 8 个副本槽，合计 184 槽，通知程序原先仅启动 128 个线程。另一个容量补丁让 129—256 槽使用 256 个线程，保留原来的专家编号与通信数据算法。这项改动已属于本地 kernel 启动适配，因此后续结果必须标作“v1.2.1 加本地容量补丁”；是否通过仍以新的两卡结果文件为准。

H=128 的缩小诊断形状曾在返回结果时失败，记录保留。代码审阅发现该形状使返回程序中的一轮处理只覆盖半个 32 线程小组，而循环内部要求整个小组同步；这是待验证的原因。当前只按 H=7168 的实际测试结果判断目标形状，不修补或掩盖 H=128 的错误，也不把小形状认定为已支持。

测量范围、正确性和原始证据

本轮原生对照设置 rt=0，即关闭根据流行度主动增加的专家副本；仍保留均衡负载所需的副本。额外槽上限为每卡 8 个。因此结果比较的是这一原生配置，不能推广成优于所有 MoonEP 参数选择。
