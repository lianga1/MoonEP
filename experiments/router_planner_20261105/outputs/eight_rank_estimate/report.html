24.98% 是真的，但只表示 token 流量

一个 token（输入的一行向量）在同一张远程卡执行多个专家，只传一份向量。这次减少的是这样的“token—远程目的卡”份数，原有计算任务仍恰好执行一次、每张卡计算对总数仍相等。

每卡 8 个额外槽限制的是接收端。例如第 3 层，优化后某个专家原属卡要向多个目的卡合计送出 21 份，而原生最忙卡是 4 份。因此总流量平均分给八卡会低估权重和梯度热点。

时间按每张卡的收发量计算

D[s,d] 表示原在卡 s 的 token 有多少份需去卡 d，本地项置零。C[h,d] 表示原属卡 h 要向卡 d 复制多少份专家。先从真实计划建立这两个 8×8 表，再为每种传输换算字节。返回方向把行和列对调。

TX[i] = 第 i 行之和：卡 i 要发出的字节
RX[i] = 第 i 列之和：卡 i 要收到的字节
该阶段时间 ≈ max(所有 TX，所有 RX) ÷ 该类传输的单向有效带宽
八层时间 = 每层先这样算，再把八层时间相加

默认假设八卡在同一台 NVSwitch 服务器，八卡能并行收发。不能拿全系统字节除单卡带宽，也不能先把八层流量汇总再平均。这里的模型忽略协议头和对齐填充；两卡有效带宽包含实际 kernel 的本地读写及同步，但不保证八路并发仍有同样效率。

NVIDIA Hopper 官方说明中的 900 GB/s 是每 GPU 双向带宽。本报告使用实测单向有效值，没有把 900 GB/s 代入单向公式。

自己调整带宽和 planner 成本

以下实时计算仍使用原八卡逐层矩阵。带宽为每 GPU 单向有效 GB/s；planner 输入是优化方案相对所选 MoonEP 的每层额外时间。

共享端点服务近似把同一卡的权重服务时间和前向 token 发送服务时间相加再取最大值。它考虑端点重叠，但不是经过硬件验证的并发模拟器。

kernel 测量保留八卡维度

两张物理 H200 各自测原始八逻辑卡维度。每个来源实际扫描 16,768 个 token，方向仍为八卡。逐层先取每个来源的重复中位数，再取来源与物理卡中最大值；不把全量耗时除八。

八层均值：四轮交换从 179.16 μs 降到 86.31 μs，下降 51.8%；新增完整八卡驻留选择组件约 887.84 μs。可见 170 μs 不能沿用为八卡新增 planner 总成本。

驻留选择包括 256 个样本的读取、28 对卡的组计数、前两组筛选以及共享预算的贪心选择。交换复用“每个 token 可在哪些卡执行”的位图，用分块计数及前缀和代替排序；每个 token 仍只提交一个最佳提议。

这些是组件实测。所有来源先在 GPU 上联动，逐轮验证实时计数、配额和最终执行卡；来源计时阶段则条件化使用已验证的全局计数。尚不包含真实八卡统计汇总、样本收集、专家表广播和最终地址发布，也不是完整八卡原生 MoonEP planner 比较。

目前不能宣称所有层都取得完整收益。M=1 的基准估算相对 rt=0 在额外 planner 为零时仍亏；降低扫描时间有价值，但不能独自消除权重和梯度的这笔成本。后续选择专家时应同时约束新增副本量、原属卡发送热点，以及每份副本实际消除多少远程发送。

更多微批能否摊薄成本

若每次更新做多个微批，并能持续保留每层相同版本、相同位置的权重和累积梯度，可以让权重刷新及梯度归并每次更新只做一次；当前模型的总字节在重复相同流量两次时可能回本。但 MoonEP 的额外槽池跨层复用，不能只把微批数改为 2 就假定副本一直在。需要额外存储、调整执行顺序或明确的版本缓存，映射变化时还须先归并旧梯度。这里不把它计作已实现收益。
