# 计入权重刷新后的多机 EP planner

2026-11-02。用户确认训练场景、每次权重更新后刷新副本，并同意以 H=7168、专家中间维度 I=2048、BF16 权重测试。4 台机器 × 8 卡、全组 131,072 token、top-8、352 专家、每卡 32,768 个执行 pair、额外专家上限 B8 均保持不变。

**结论：上一版大量新增副本的 rail planner 在当前冷刷新合同下没有净收益。继续优化后，推荐先用节点净配额优先、集中跨机副本、再机内均衡的简单版本。两个 trace 派生场景在含权重、梯度与假定规划开销的模型中分别节省 11.02% 和 14.56%。五个 home-only 合成场景没有找到可盈利的动态复制方案，提前退出。**

这些数字是未校准的 CPU 仿真，不是 GPU 实测，也不是完整训练迭代加速。trace 派生输入保留原始 top-k，但 32 卡源映射是合成的。最终主方法是 `weight_aware_simple`，不会按场景从多种候选中事后挑最优值拼接结果。

## 成本合同

完整 gated MLP 专家按三个矩阵计：

\[
W=3HI\times2=88,080,384\ \mathrm{B}=84\ \mathrm{MiB}.
\]

每次 optimizer 更新产生新版本；所有实际执行的非 home 副本都需刷新，**seed 自身的副本同样收费**。预留但没有执行的槽位不传。没有把跨更新缓存当成免费缓存；没有迁移 optimizer state。只需要当前版本权重的执行副本，不移动 home 身份。

权重从 home GPU 出发，同一专家对同一目标节点只走一次 RDMA，再在目标节点经 NVLink 分发。梯度先在执行节点归并到 home rail 的 relay，然后反向 RDMA；默认 BF16 梯度，另跑 FP32 梯度。目标 relay 可使用分块暂存，不必是该专家的执行 rank。此处显式假设支持节点级广播/归并，未模拟归并算术、HBM 竞争、scales 或协议字节。

token 传输仍为源 rail RDMA → 目标节点 NVLink，没有新增源端 NVLink 负载重分布。权重也没有源端换 rail。

主结果每次更新一个 128K microbatch。设前向 dispatch、GEMM、combine 分别为 D、C、R，模型额外假设反向使用同样大小与路径的两次 token 通信，反向 GEMM 为前向的两倍：

\[
T_{update}=T_W+M(2D+3C+2R+\Delta P)+T_G.
\]

M 为同一权重版本下的 microbatch 数；M>1 时在副本处累积梯度，每更新末归并一次。模型采用阶段屏障，没有隐藏预取。NIC 单方向 40 GB/s，NVLink GPU 端口单方向 150 GB/s，权重块 1 MiB，激活块 128 token；其余参数沿用旧仿真。另保存共享端口累计服务的乐观下界，它不代表已实现的重叠调度。

\(\Delta P=128\ \mu s\) 是新增 GPU planner 的**假定预算**，不是测量，也不是从 CPU 时间换算。主方案提前退出时另计假定 2 μs 检查成本，未标成零开销。所有方法共同的 seed planner 未测量、作为共同项省略，因此所报百分比不含共同 planner；绝对差值仍是该模型内的比较。router、其他层、optimizer、真实反向内核和数值 MoE 都未验证。

## 旧方案为什么失败

旧单轮 B8 在 fanout 偏斜 1.5/2.0 场景分别新增 240/248 个活动副本，权重 RDMA 为 21.14/21.84 GB。最忙 NIC 的权重 payload 服务下界均为 **17.616 ms**，而原来仅比较前向 token 时省 1.653/2.602 ms。当前权重刷新屏障合同下，成本无法覆盖。

这个服务下界不是任意跨层预取下的新增关键路径时延。旧 FCFS 整块调度还会放大队头阻塞，所以同时保留精确字节、端口下界和排程结果，不能把模拟的 75.8 ms 权重排程当硬件预测。

| 场景 | seed 训练段 ms | 旧单轮 B8 ms | 新简单版 ms |
|---|---:|---:|---:|
| 合成 fanout 偏斜 1.5 | 33.623 | 144.262 | 33.625，提前退出 |
| 合成 fanout 偏斜 2.0 | 42.769 | 161.001 | 42.771，提前退出 |
| trace 派生 L00 | 42.847 | 128.581 | **38.126** |
| trace 派生 L07 | 52.116 | 142.691 | **44.528** |

减少预算至 B2/B4 也重跑了七个场景，M=1 下均未获得净收益。纯已有驻留交换没有权重增量，但只有小幅 token 收益；扣除规划预算及重分块排程变化后，也未成为主方案。

## 新算法：先解决节点净缺口，再做机内精确均衡

1. 复用 expert demand 表，计算 home rank 与 home node 的计算净盈亏。若 home 已精确均衡且 seed 没有额外执行副本，保持 seed，不创建仅为减少 token 流量而付费的副本。
2. 先补齐节点净计算缺口。优先复用目标节点已有的同专家副本，其次复用目标 GPU 的副本，再选能一次填充较多配额的大专家，尽量少产生 expert/目标节点权重拷贝。
3. 允许捐出 pair 的 GPU 暂时不足额；稍后用同节点其他 home 专家补齐。**这是规划顺序，不是 token 先机内再机间的传输顺序。** 先把每个 rank 单独补平再跨节点，会留下大量小额外溢，每份都要搬完整专家；这一失败消融在代码中保留为 `rank_first`。
4. 节点净配额平衡后，只在节点内补齐各 GPU 配额。硬性保留每 GPU 32,768 pair 和 B8，无法在预算内实现时回退合法 seed；回退也不自动免除已经执行的规划成本。
5. 对每个专家分配来源配额，先 source GPU、再 source node、最后其他节点；用稳定 occurrence prefix 得到最终 owner。所有 token 都从原来的源 GPU 直接按规定路径发送。

| 项目 | L00 seed → 新版 | L07 seed → 新版 |
|---|---:|---:|
| 全部活动非 home 副本 | 33 → 33 | 33 → 35 |
| 新版每 GPU 最多额外专家 | 3 | 5 |
| 权重 RDMA 拷贝，按 expert/目标节点去重 | **16 → 4** | **24 → 7** |
| 新版跨机活动执行副本，按 expert/rank 计 | 5 | 15 |
| 权重刷新排程 ms | 7.118 → 4.748 | 11.858 → 7.125 |
| 副本梯度归并排程 ms | 8.267 → 4.740 | 11.032 → 7.140 |
| 计入 128 μs 新增规划预算后的净节省 ms | **4.721** | **7.589** |

新版节点间迁移的执行 pair 分别为 27,853、203,268，达到各自 home 节点净盈亏决定的必要 pair 数下界。这是计算配额迁移下界，不是整个通信或端到端时延的全局最优证明。

## 所有传输都纳入后，指标并非一起改善

| 项目 | L00 | L07 |
|---|---:|---:|
| token RDMA 拷贝变化 | +0.35% | +5.14% |
| token NVLink 拷贝变化 | −0.69% | −1.08% |
| 权重 + 梯度 + 前反向 token 的 RDMA 总量 | **−8.82%** | **−8.39%** |
| 全部 payload 的最忙 NIC 端口字节 | **−8.14%** | **−7.74%** |
| 全部 payload 的 NVLink 总量 | +0.37% | +0.34% |
| 全部 payload 的 rail 最大/平均 | 1.113 → 1.119 | 1.111 → 1.114 |

收益主要来自少搬跨机专家，不能称为所有 rail 比值更均匀。最大端口的绝对压力下降，但分母也改变，max/mean 略升。机内 token 流量少了一些，新增机内权重/梯度抵消了这部分总量收益。最终目标应以端到端关键路径和实际端口压力衡量，而不是单独优化比值。

五个 home-only 合成场景下，如果不新建副本、不改变 home placement、不重分源 token，那么每个专家只有唯一合法执行 GPU，没有免费更换 rail 的自由度。本轮测试的新副本方案均不划算；主方案保留原流量与 1.5/2.0 偏斜，付出模型中的 2 μs 检查。**该原始偏斜问题尚未获得有净收益的解法**，不是宣称所有可能的布局/预取算法均不可能改善。

## 复用轮数和梯度精度敏感性

下表是同一 workload、同一 placement 在同一权重版本内重复 M 次的假设试验，不是真实连续 microbatch trace。所有数据仍保存；不跨 optimizer 更新摊销。

| 每更新 microbatch 数 M | L00 净节省 ms/更新 | L07 净节省 ms/更新 |
|---|---:|---:|
| 1 | +4.721 | +7.589 |
| 4 | +1.192 | +4.482 |
| 16 | −12.923 | −7.944 |
| 64 | −69.382 | −57.649 |

本模型的净节省可写成 L00：`5896.810 − 1176.229×M` μs，L07：`8624.368 − 1035.521×M` μs。因 token 段略变慢，新简单版分别只在 M≤5、M≤8 时为正。不能把 M=1 的选择直接用于较大梯度累积窗口。主报告中的盈亏边界由此公式决定；早期 JSON 的 `break_even...` 字段只表达随 M 增大由亏转盈的情形，不能把其 null 读成 M=1 没收益。

FP32 副本梯度敏感性下，M=1 的 L00/L07 为 51.142→42.866 ms、63.176→51.638 ms，分别节省 16.18%、18.26%。权重仍为 BF16。BF16/FP32 梯度都是模型合同，未由训练代码 dtype dump 验证。

对于主 M=1，新增完整 planner 的可用盈亏预算分别约 4.849/7.717 ms；这说明净收益对假定 128 μs 不敏感，但**并不证明 planner 满足 MoonEP 两倍时延约束**。2×约束仍必须单独用同一 32 卡系统实测。

## 复杂度与候选收缩

简单主版本没有 LP、没有全 token 比较排序。节点/rank 配额是小表贪心；实际 L00/L07 各 33/35 次配额转移。每步扫有限的 rank/home-expert 表，来源配额参考实现有 O(E R²) 小表工作；token 映射是稳定计数加 O(TK log R) prefix 查询，R=32 当前每 pair 六次探测。CPU NumPy 使用密集来源表，kernel 可以使用非零区间，但本轮未实现 GPU 压缩布局。

首选实现方式是复用 MoonEP 的统计与 C1/C2，把节点感知配额替换进 A3/A4，最终只重建一次地址。CPU 原型未证明 2×门槛；小表决策和跨机协调也必须计入完整 planner，不能只计 pair kernel。

另实现了 `optimize_weight_neutral`：每个已分裂专家取一条 rank 边、每 pair 一个候选、每 token 一个提案、同专家反向等量交换，O(TK+RE)，严格保持 expert/rank 数量、权重/梯度与 padding。单独使用时净收益不足，本轮不把它放入简单主路径。

还试了保留原 chunk 成员及端口提交顺序、只删除传输的排程版本。它能使通信阶段单调不增，但在层次主计划上额外仅省约 6.1/2.1 μs 的训练段排程时间，收益不足以支持更复杂的默认路径。真实传输系统还需提供可复用的提交顺序；CPU 从 seed 事件排程获得顺序不代表低成本 GPU 实现。此版本保留在 `weighted_final`，不用于主结论。
