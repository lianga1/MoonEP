# 32 SM planner：融合与未融合逐阶段实测复算

本次比较的是同一台 omni-dev 的 8 张 H200、同一份 `802af3f` 运行代码、同一批 8 层 router trace。两档都固定候选上限 128、四轮交换、每次 kernel 最多 32 个线程块；唯一配置差异是 `fuse=False/True`。N=134144，R=8，S=16768，E=352，K=8，采样 256，每类保留 2 组，B=8。

**结论：32 SM 下，融合仍慢约 26.722 μs（3.06%）。主要新增耗时来自“提议与稳定序号合并”和“大计数表通信合并”两处，合计约 45 μs；其他阶段与 kernel 之间的空隙有所减少，抵消一部分后，完整 planner 净慢约 27 μs。**

## 总延迟与仪器开销

单位均为 μs。正式延迟沿用原来的无插桩 CUDA Graph 方法：每 rank 10 个样本，每样本回放 5 次；先取每 rank 中位数，再取最慢 rank，最后对同一 8 层求平均。前、后两次测量用于观察诊断期间的漂移。表中“前后中点”只是两次正式结果的平均，不是额外一次测量。

| 口径 | 未融合 | 融合 | 融合−未融合 |
|---|---:|---:|---:|
| 正式无插桩：诊断前 | 871.014 | 898.680 | +27.667 |
| 正式无插桩：诊断后 | 873.831 | 899.608 | +25.777 |
| 正式无插桩：前后中点 | 872.422 | 899.144 | +26.722 |
| 稳态 trace：第一核开始至最后核结束 | 860.293 | 888.147 | +27.854 |
| 稳态 trace：各 kernel 时间之和 | 851.009 | 881.996 | +30.987 |
| 稳态 trace：kernel 之间的空隙 | 9.284 | 6.150 | -3.133 |
| 阶段 events：完整测量区间 | 1000.680 | 1028.190 | +27.510 |

阶段 event 节点本身会扰动执行：相对稳态 trace，总计增加 140.387/140.043 μs；相对正式无插桩前后中点，增加 128.258/129.046 μs。这就是“约 140 μs”开销的准确参照。两个参照不能混用，也不能把 140 μs 按比例从某个阶段里扣掉。以下瓶颈分析主要用稳态 trace；event 数据用于边界与结果一致性验证。

稳态 trace 比正式前后中点短 12.129/10.997 μs。两者测量边界和启动方式不同：trace 只覆盖第一核开始到最后核结束，正式计时还包含 Graph 提交相关间隙，且每批只有 5 次回放。这里不把差额强行归到某一个 kernel。trace 所观察到的融合差额为 27.854 μs，与正式差额接近。

## 两处主要回退具体在哪里

第一处是四轮提议与稳定序号。未融合的 proposal 核扫描每个本地 token，产生唯一交换提议；ordinal 核为同一类提议生成稳定的位置编号。融合将两项放进同一个核。

| 四轮累计 | 未融合 | 融合 |
|---|---:|---:|
| proposal 单核 | 102.903 | 合入下项 |
| ordinal 单核 | 25.043 | 合入下项 |
| proposal + ordinal 合计 | 127.947 | 150.384 |
| 后续 block prefix 前缀核 | 21.624 | 21.608 |

前缀核基本没有变化；回退发生在 proposal+ordinal 融合核本身。少一次 kernel 启动并没有抵消这个核增加的执行时间。trace 中两版均为 32 个线程块、每块 256 线程；融合核每线程 54 个寄存器、共享内存 36896 字节，未融合 proposal 是 52 个寄存器/0 共享内存，ordinal 是 32 个寄存器/36896 字节。这些资源值说明融合改变了单块工作组织，但仅凭这些数字不能断言寄存器或某种缓存失效就是主因；需要独立改动验证。

第二处是四轮计数表通信。每轮收集所有 rank 的交换提议数量，后续用它生成双向匹配配额。

| 四轮累计 | 未融合 | 融合 |
|---|---:|---:|
| 本地 payload 复制及 system fence | 8.364 | 融入同一个核 |
| 两次 peer barrier：发信号、栅栏及等待 | 42.756 | 融入同一个核 |
| 读取 peer payload | 11.437 | 融入同一个核 |
| **合计** | **62.557** | **86.156** |

融合核使用 32 个线程块的 cooperative grid，包含本地复制、grid 同步、两次 peer barrier 与远端读取。未融合把这些任务拆成四个 kernel；其中复制只需要 5 块、barrier 各 1 块、读取 32 块。时间说明这项合并在当前大小/32 块限制下不划算，但没有把融合核里的纯传输、grid 同步、到达等待分开计时。

**单段归因受 rank 选择影响。** 同步会把较快 rank 的等待归在通信阶段，而较慢 rank 更多时间花在前一计算阶段。为避免只挑一个 rank 导致误解，还对全部 8 rank × 5 保留回放 × 8 层求平均；每个完整回放仍先逐项相加，再求平均：

| 融合增加的时间 | 按每层最慢 rank 的完整中位回放 | 全部 rank/replay 平均 |
|---|---:|---:|
| 四轮：提议、稳定序号、前缀 | +22.421 | +29.517 |
| 四轮：计数表卡间收集 | +23.599 | +15.145 |
| 两段合计 | +46.020 | +44.663 |

两种统计的共同结论是：这两处合计约多 45 μs；不能把通信段的所有增加都叫成“网络带宽变差”。全部 rank/replay 平均总时长为 859.678 → 888.173 μs，与上面的完整中位回放结果接近。

## 通信、计算和等待能分到什么程度

未融合可以直接读到独立核的时间：本地 payload 复制/栅栏约 14.412 μs，peer payload 读取/归并约 19.889 μs，独立 barrier 核总计 84.740 μs。最后一项包括 planner 外围三次原生同步及各表通信的 barrier，包含信号、栅栏和等待，不能称为纯等待。

融合后的 peer 表通信整体约 124.584 μs，内部混合复制、读取、grid 同步和等待；只能单列外围独立 barrier 的 15.404 μs。所以独立 barrier 从约 85 μs 变成 15 μs，**不表示等待减少了 70 μs**，大部分只是移进融合核了。原生 seed 也始终含内部通信/等待，本报告没有把它包装成纯计算。

## 数据与正确性核验

- 核验 256 个压缩 trace 的 SHA256，并重新从 eager 的 CPU 标签和 CUDA correlation 建立映射。运行时记录的 parser/harness 哈希与本地解析源一致。GPU kernel 顺序逐次匹配；每次未融合 104 核、融合 64 核，全部 grid ≤32、无 NCCL 核。
- 重新解析 896 次完整 trace 回放，其中前两次/每组均丢弃，保留 640 次。最大“kernel 总和 + 间隙 − 完整 span”误差为 0.004898 μs，来自大时间戳浮点精度。
- 复算 1280 个阶段 event 样本，并与 16 份每 rank 原始文件交叉核验。最大闭合误差 0.00007683 μs。事件位于 Graph 内；每个正式阶段样本之前有 2 次不计时生产 Graph 起跑对齐。
- 两档全部完整 snapshot 比较通过，共直接比较 1664 个数组哈希；与前次正式交付的 dst、专家复制表、zero fill、remote stats、cu、owner、support、source info、history 共有 1152 个哈希比较，全部相同。
- support、有效 history 与全局四轮 owner 直接匹配保存的 CPU oracle，共 272 次哈希核验；这次没有重新运行 CPU 仿真。实际物理地址、每卡任务量、专家容量、去重标记、来源元数据等 GPU 独立审计全部通过，四个诊断前后阶段均无输出差异，没有 fallback。
- 八层累计 token-目的卡传输计数均为 3,887,660，原生 MoonEP 为 5,054,165，下降 23.0801%；专家副本计数累计 434。两档与原交付一致。这是 planner 计数，未测训练权重、梯度、token payload、GEMM 或完整训练净收益。
