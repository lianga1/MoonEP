# 32SM planner：融合回退原因与八卡分治优化

本轮比较固定八张物理 H200、每卡 16,768 个 token、E=352、K=8、采样256、每类保留2组、候选128、交换四轮、每卡32SM上限。Buffer的H=256，仅执行规划，不传输激活数据。所有结果都来自 omni-dev 同一台机器。计时范围包含原生起点、候选选择、四轮交换、卡间统计通信、地址生成及发布；不包含专家/token/梯度载荷、GEMM或优化器。

本轮交付结果：**新版选择性融合 776.764µs，比旧32SM未融合版 850.802µs 下降 8.70%，比旧融合版 889.482µs 下降 12.67%。** 候选、四轮交换、每个任务地址和专家副本选择均保持一致。

| 完整 planner | 八层平均 µs | 核数量/次 |
|---|---:|---:|
| 旧802未融合，前后对照中点 | 850.802 | 104 |
| 旧802融合，前后对照中点 | 889.482 | 64 |
| 新版未融合 | 797.038 | 109 |
| 新版选择性融合 | **776.764** | 91 |

每层先取每卡10个样本的中位数，再取八卡最大值，最后平均八层；每样本含5次Graph回放。前后中点是两次测量的平均，不是置信区间。当前32SM建议 `SampledPlannerConfig(candidate_limit=128, rounds=4, sm_limit=32, fuse=True)`；默认仍为 `sm_limit=0, fuse=False`。

## 为什么上一版融合慢

在原始802版本上，未插入阶段计时的完整 planner 为872.422µs（未融合）和899.144µs（融合），后者慢26.722µs、3.06%。这是本轮重新测得的基线，不复用上轮数字。

稳态 trace 的完整、可闭合向量表明，主要差额来自四轮提议（含稳定编号和前缀）增加22.421µs、四轮计数汇总增加23.599µs，其他阶段和kernel间隙抵消一部分，最终净慢约27µs。

- 提议融合将复杂提议计算与块内稳定编号放在一起，改变每个线程块承担的工作；前缀扫描自身几乎不变。寄存器/共享内存记录只能说明资源形态，不能单凭它们断言某种硬件停顿是唯一原因。
- 大表通信融合引入协作网格同步，并没有消除跨卡的两次同步。独立完整通信实验也显示大表原来的四次启动更快；小标量状态单块融合更快。
- 慢rank会让其他rank等待，所以单独的通信阶段带有到达时间差；将提议和随后的汇总合看，额外耗时约45µs的结论保持一致。

完整原始阶段表、逐层逐卡记录与复算见基线分析。外部CUDA事件插桩会把完整路径额外拉长约129µs，不能把插桩总和冒充正式延迟，也不能减一个固定常数校正。

## 这次改什么

1. **按记录编号把频率计算分给八张卡。** 八卡先获得相同样本表，然后rank r只负责编号除以8余数为r的记录。每条记录仍和全体样本比较，哈希相等后仍检查真实专家列表，计数和重复记录代表完全不变。例如本例有28×256=7168条记录，每卡负责896条；rank0负责0、8、16…，rank1负责1、9、17…。最后收集各卡负责的结果，恢复原顺序，再执行原来的候选排名和贪心选择。没有减少采样或候选，也没有用本卡频率代替全局频率。
2. **把候选覆盖关系压成位图。** 保留候选内的专家位置可以用32位整数表示时，复用预计算的覆盖关系和已驻留状态，通过位运算计数，减少重复检查专家集合。选择顺序、平局规则、预算、历史保持一致；不满足编译期范围的模型继续原实现。
3. **用已有计数表生成地址起点。** 原生顺序已按专家稳定排列，目标卡分组也稳定，因此对“卡×专家”的计数做前缀和就等价于再次扫描全部任务寻找起点。本例将再次读取134,144个计算对改成处理2,816个计数。8个warp分别处理8张卡的桶，只在合计桶总数时同步。输入计数也合并同一warp内相同键的原子更新。
4. **只保留测量有效的融合。** `fuse=True`仍融合小标量通信、候选初始评分/分段排序、交换配额、布局准备、最终计划选择；提议与稳定编号拆开，大表通信恢复独立启动，token分块仍为256。

最坏频率比较工作量可写成每卡 O(28×d²×K/8)，再增加 O(28×d) 的结果汇总；这里d为采样数，K为每token专家数。它是工作量上界，不是延迟除以8的公式。组件测量包含汇总的频率阶段平均42.853→32.188µs。

分治并不把整个planner耗时除以8。频率比较的任务可以独立分片；贪心第i次选择依赖前i−1次已用的副本预算，不能无条件同时决定。当前仍在每卡重放同一贪心，避免每选一次副本都新增跨卡同步。

频率分治新增每卡896个int32的输出、8×896个int32的收集区，共31.5KiB工作区。每卡逻辑上额外读取其他七卡24.5KiB频率数据，八卡合计196KiB，另有同步协议；这部分已经计入完整planner计时。token传输计划和权重副本数量保持不变，不意味着planner元数据流量不变。

自动分治目前仅用于E352/K8/采样256/每类2组/正候选上限/SM32的完整八卡路径；其他配置继续本地频率计算。既有模型配置和动态参数接口保持可用。

## 尝试过但没有采用

组件测试中，64/128 token的小分块扩大了直方图与前缀工作区，反而慢于256分块。把每线程候选包数量从11缩成1，虽然寄存器从128降到40，却使本阶段从约170µs增加到222µs；因此只保留为诊断入口。把大表通信压成1/2/4/8个协作线程块也更慢，没有作为默认策略。

这些是组件微基准，不与完整planner时长相加。所有失败或较慢的实验及源文件快照均保留。

## 正确性与通信收益

- 60项独立pytest用例通过：配置24、组件9、分块5、八卡公开接口与恢复17、兼容5；分布式用例在八个进程执行，不按8倍重复计数。
- 正式记录复算4608次数组哈希比较，九项完整plan数组与旧版一致；1136次CPU oracle核验通过，无回退。
- 八层原生MoonEP远程token-目的卡次数5,054,165，新算法3,887,660，下降23.0801%。同一token去同一远程卡执行多个专家只计一次。这是精确计划统计，不是实测网络耗时或完整训练收益。
- 八层专家副本累计434，与旧算法相同，因本次优化新增的权重/副本梯度传输量为0；不是说新算法相对原生MoonEP没有专家传输成本。新增196KiB逻辑频率表远程读取已计入planner。
- 16份预算trace和256份阶段trace重新校验，每次launch及同时启动的CTA总数均≤32，无NCCL kernel；保留640次稳态回放、1280个event样本。32SM是单个在途planner的上限，不固定物理SM编号。
- 原始输入是八层router fixture；交付包含其哈希与CPU oracle，不重新公开私有NPZ。没有测量完整训练吞吐、权重刷新、梯度归并或GEMM。

## 复现与证据

无需GPU、PyTorch或私有fixture即可独立核验已保存结果：

```bash
python3 experiments/sm32_divide/verify_delivery.py --check-sources
```

源码校验需要干净checkout；若工作区有无关修改，省略`--check-sources`只验证证据。脚本会临时解包、核验源文件/原始文件哈希，重新解析trace、重算各rank中位数、比较CPU oracle，再与交付结果逐项比较。

重新运行GPU实验需同机八卡NVLink环境和原始fixture。`run_final_03.sh`记录完整命令与执行顺序，包含旧版前后对照、新版两配置、阶段采集和全部正确性测试；路径应按自己的环境修改。`candidate_payload_03.tar.gz`是运行时与测试源码的冻结快照，哈希见`candidate_manifest_03.json`。

`baseline_profiles_frozen03.tar.gz`保存旧版阶段原始记录及冻结解析器，`final03.tar.gz`保存最终原始样本/trace/测试日志和退出码，`components_diagnostics_02.tar.gz`保存组件实验。01/02源码快照与失败的第一次profile解析尝试保留，未混入最终结果；慢于基线的实验也未删除。
